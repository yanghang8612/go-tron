# 冷化负荷预算修复与验证

此次处理针对 [9 月 8 日复查](genesis-sync-status-2026-09-08.md) 确认的积压与长合并问题，尤其考虑数据库进入 20M 以后，固定块数不再代表相近工作量的情况。没有改变历史保留、内部文件格式、共识或查询语义，也不清空当前数据库。

实现细节与验收边界见 [工作方案](../superpowers/plans/2026-09-08-io-bounded-history-catchup.md)。主要行为为：

- 普通历史与独立事件日志根据真实构建耗时、输出字节和新鲜负荷反馈调整下一批；密度增加时立即收缩，恢复时通常每批最多增加 25%。1–3 个单位的极小批量若容量确实允许，可增加一个单位，避免取整后永久停在一块。
- 写阻塞、L0 或 memtable 接近停止写入条件时，共享重任务门拒绝新任务。设备指标独立采样且明确区分未知；单独的 busy 百分比不会触发硬拒绝。
- 已完成构建但后置操作失败，仍保留真实密度观测；未完成构建的失败用独立上限缩小下一次尝试，不冒充成功记录。事件日志复用完整外层完成握手，不能通过 active/idle 切换绕过期限。
- startup/最近同步的一分钟继续保守使用在线预算，避免短暂 peer 状态切换立即触发大合并或 latest 全扫描。
- 繁忙合并只处理原始叶，最多 512 MiB 物理输入、2 GiB 逻辑正文、800 万记录和 16 个源；它自己持共享重任务锁，并拥有独立恢复与一次性优先机会。
- 大合并成本不再进入普通历史的恢复等待。普通历史的昂贵完整区块仍按真实成本恢复，不能通过截断等待将维护占空比悄悄放大。history 的目标占空比不是整盘或所有后台任务的总占空比。

## 本地验证

最终实现主体的全仓 `go test ./... -count=1 -timeout=300s` 通过：**54 个有测试的包、13 个无测试的包、0 失败**。相关 maintenance、Pebble、snapshots、pruning、CLI 定向 race 全通过。检查过程中发现并修复了事件日志状态切换/结果覆盖、小整数批量不能恢复、未完成构建重复大批量三类问题，并加入真实事件日志、清单段数和密度反馈回归测试。

源树没有运行生产数据转换。本地测试的 fixture 都是临时数据库和不可变段；日志保存在 `build/benchmarks/20260908-history-budget/validation/`。合并独立唤醒接线另以真实 16 叶 Runner 集成测试检查，要求先运行安全裁剪回调、不启动额外历史构建，并保持原历史准入截止。

## 同输入合并实验

环境为 Apple M1 Max、Go 1.27.1、darwin/arm64、GOMAXPROCS=10。使用确定性的 **256 叶 × 每叶 64 条 × 每条 4 KiB Prev**，V2 压缩格式；总逻辑输入 **69,217,280 B**。旧路径一次合并 256 叶，新路径执行 **16 次、每次 16 叶**，两者都处理全部输入，并非只比较新路径前 1/16 的工作。

| 指标 | 256 叶一次合并 | 16 叶 × 16 次 |
| --- | ---: | ---: |
| 最长单轮合并耗时 | 2.612 s | **0.282 s** |
| 全部合并耗时（不含调度等待） | **2.612 s** | 3.649 s |
| 最大单轮累计分配 | 345.1 MB | **32.7 MB** |
| 累计重写逻辑输入 | 69,217,280 B | 69,217,280 B |
| 最终历史文件数 | 1 | 16 |
| 最终物理输出（含 companions） | 663,241 B | 644,545 B |

此次短批次将最长单轮缩短 **89.2%**，但全部合并耗时增加 **39.7%**。这是减少连续占用、增加让出资源机会的取舍，不能表述为总合并吞吐提升。累计分配不等于 RSS 峰值，文件大小也不等于内核实际 IO；输出大小约减少 2.8% 只适用于这个高压缩合成样本。

两种路径的 **16,384 条记录及 512 次跨叶边界索引查询全部通过**；每个原始叶只参与一次合并。语义摘要均为 `02e31a5ccd88d1ba7d089497ba07b7d0b2769b8a5e998545dfcc0a165062bac6`。V5+ 的 Seq 属于段内派生序号，实验先按各自 manifest 验证，再在语义摘要中标准化，其余字段严格比对。

可复现入口为 `core/state/snapshots/history_budget_benchmark_test.go`，原始输出、结构化 JSON 和限制说明在 `build/benchmarks/20260908-history-budget/`。这是本机热缓存单次合成实验，**不是 20M 主网 A/B，也不证明导入延迟或最终全链容量**。

## 线上验收口径

服务器必须 pull 确定提交后以 Go 1.25.5、CGO/Sapling 原生测试和构建，保留当前 datadir、维护锁与磁盘保护。新旧进程分别采集导入、冷化、裁剪、积压及整盘 IO，复验原固定历史账户。

线上需要同时观察正文 freezer、独立事件日志和状态合并，不能用 history 自身较低的目标占空比推断整盘已被限速。后续实际进入 20M 及巨大代理/委托记录阶段仍需复验；当前高度的结果只证明部署与当前负荷下的行为。

## 首次部署后的完整窗口与追加修复

不能把此次短批次修复表述为“积压已解决”。采用持续更新的 **head − published** 距离观察三个完整五分钟窗口，得到：

| 北京时间 / 版本 | 导入块/秒 | 冷发布与热裁剪块/秒 | head − published 变化 |
| --- | ---: | ---: | ---: |
| 09:55:43–10:00:43，旧版本 | 48.61 | 30.76 | **扩大 5,353 块** |
| 10:13:42–10:18:42，0aad093f | 42.20 | 24.59 | **扩大 5,282 块** |
| 10:21:52–10:26:52，0aad093f | 47.14 | 49.14 | **缩小 600 块** |

所有窗口 published 与 pruned 一致，cold/prune/lifecycle 错误计数增量均为零。后两个窗口高度已在 7.3M，区块负荷、缓存与后台阶段不同，这些是线上观察，不是相同区块/相同缓存的性能 A/B。

第一段新版本窗口前约 135 秒，cold 为 54.65 块/秒、import 为 43.53 块/秒；但 **10:15:57–10:18:42** 冷发布、裁剪与 pass 计数约 165 秒不变，后续约 150 秒几乎全部冷化指标不更新。eligible 也停更，使 `eligible − published` 产生“减少 1,574”的误导性结果；实际 head 距离扩大 5,282，不能引用该 eligible 差值认定追赶成功。

普通构建已缩到数百至千块、约 2–6 秒，并随压力改变 20% / 33% / 60% 目标占空比。窗口内完成两次三来源合并，物理输入分别 **179,211,240 / 181,030,752 B**，逻辑输入 **528,779,333 / 537,883,566 B**，记录 **7,341,108 / 7,464,522**，独立恢复约 **57.4 / 58.6 秒**。这证明小合并与独立恢复生效，但没有消除其他阶段的连续占用。

日志记录 **10:19:15** 正文 freezer 完成 65,536 块整段。源码审查发现事件目标规划在申请 heavy gate **之前** 调用阻塞的 `CanAppendV2Direct`；它等待 `writeLock.RLock`，而 direct `MigrateV2` 从整段转换开始至结束持有写锁。这是可确定重现、与静默时段吻合的阻塞路径。goroutine 是整段完成后才采到的，已回到 select，不能把它当作停顿现场的直接栈证据。

追加修复将同步规划改为一次三态非阻塞探测，同时尝试 writeLock 与 v2Mu；未能观测明确返回 deferred，并在 3 秒后重试。未知不能等同于“无需外置日志”，也不能发出已追齐的 freezer handoff；现有更晚历史恢复期限保留。history/event 被占用 gate 拒绝且尚无 cooldown 时同样补有界重试，原强校验与查询路径不变。

这项修复恢复规划响应、可观测性与完成后的及时重试，**不允许状态 cold 与正文 freezer 穿过共享门并行运行**。65,536 块正文整段仍是剩余长任务，单次范围预算不是在途 IO 限流；后续必须按包含完整正文转换周期的总窗口判断净追赶，不能只挑选 10:21 以后短暂有利的窗口。
