# 轻量路由补建与未覆盖回退优化（2026-10-28）

## 为什么曾只覆盖 11.57%

UTC 05:27 的 3,840 / 33,180 是启动后某个时刻的补建进度，不是格式或容量上限。随后只读观测已推进至 6,592 / 33,237（19.83%）；metadata 页仍为零。轻量路由文件约 225 KB，远低于 64 MiB 编码/构建预算，观测键数也远低于 4,096，不能把低覆盖归因于轻量对象装满。

真正限制来自维护路径：每轮最多 64 个未覆盖源，经冷合并的 import-load、heavy-work gate、最少 3 秒且通常工作时长四倍的 recovery 才能再运行；补建还重新认证旧 broad 已覆盖的源。更严重的是成功 small 发布立即 return，使后面的 metadata 在整个 small 追赶期得不到运行机会。

## 改动与边界

新 small builder 读取并完整认证当前 broad 对象，从中投影全部 small 家族正成员和源覆盖，只对 exact history/accessor pairID 复用。它没有硬编码历史上观测到的 59/62 个键。metadata 仅迁移 broad 完整证明为空的源；有任何正成员、未覆盖或源替换时仍扫描权威字典。共享投影缓存命中前也认证当前物理字节。

维护改为 small/metadata 轮流获得机会；真实字典读取另外受 128 MiB 累计输入和源间约 2 秒软工作窗口限制，廉价的 metadata 迁移可填满 256 源页。一个源需完成验证后才计入覆盖；软窗口不是能中断任意单源的硬时延上限。可选内存预算不足仍为无发布，不变成维护硬错误。

未覆盖回退在同一描述符、同一批次内复用已解析的稀疏 fences 和当前目录组。现版本独立 profile 中，稀疏目录读取累计占 16.88%，目录组读取累计占 24.49%；目录项解码包含在后者，不能再相加。此处保留 CRC、范围、键顺序、字典绑定和取消检查，不用跨打开缓存绕过认证。

首查均为新进程，但未清全机 OS page cache；测试顺序及其他负载影响磁盘缓存，不能用 85→9 秒直接算提速倍数，也不能把该表称为受控冷缓存实验。反向复测是减小顺序偏差的有限补充。可比较的 9M 稳定热查由均值 8.968 秒降至 4.757 秒，约减少 47%；两次样本不是 p95 或吞吐能力结论。近 HEAD 的同覆盖候选多出约 45–76 ms，完整覆盖及补建组没有稳定复现；样本少，仍需留意轻微回归。

资源计数把改进和余下瓶颈分开：9M 同覆盖热查每次累计分配约 6.947 GB→1.676 GB，减少约 76%；进程 CPU 约 9.896→5.010 秒，减少约 49%。这不是常驻内存大小。读取系统调用仍约 128,134 次，应用读取仍约 834 MB，基本未降。因此本轮主要消除了重复目录解析和分配，并没有消除未覆盖尾段的随机 I/O。三轮补建组那次 69.477 秒首查的进程磁盘读取计数增加 2.677 GB、CPU 仅 10.890 秒；下一次仍读 1.797 GB、耗时 27.966 秒，充分说明 OS 缓存不足时尚有明显等待。计数包含该宿主进程其他运行时活动及内核预读，不等于唯一业务文件字节。

已有完整路由的 9M 热查每次约 279 MB 分配、79.6 MB 应用读取、1,341 次读取系统调用，较同覆盖回退减少约 99% 调用次数，但依然约 2 秒。35M 完整覆盖仍约 3.052 秒、589.6 MB 应用读取、101,568 次读取系统调用；因此路由完成之后仍有实际命中键的尾部和目录读取成本。本轮未另跑候选 CPU profile，不能把剩余 CPU 全部精确归到同一个函数。

三次 small 加三次 metadata 的现版本总成本分别为 5.542 / 5.876 秒，最终各覆盖 192 源；候选分别为 5.107 / 2.780 秒，最终 small 25,656、metadata 768 源。metadata 累计分配从 2.539 GB 降至 0.761 GB。此处显式调用两族用于比较 builder；不代表现版本生产 runner 实际具有公平性，也不代表候选已经完成生产补建。首轮 small 复用 25,600 个源是一笔既有证明迁移收益，不是新增尾段扫描永久加速几百倍。

## 正确性范围

严格小样本路由/历史恢复测试、物理损坏、正成员、exact pair、局部覆盖和独立字典投影对照守住负证明边界；两版维护后 canonical segment 身份和所有 progress 前沿不变。完整 HTTP 宿主固定 HEAD/hash/Tx/root。旧固定源全量 MuHash 已通过，本轮没有修改 canonical rows 或 MuHash 元素，不把只读性能实验说成新交易写入后的全量 MuHash 验收。此前延期的完整快照恢复仍未完成。

## 剩余瓶颈与下一步

当前首要顺序是把已有 broad 覆盖低成本迁入 small，并让 metadata 获得维护时隙，减少线上走回退的机会；这次代码已经实现，线上尚未应用。未覆盖源保留保守回退，不能为提速把“未找到路由”当成不存在。真实尾段受 128 MiB / 软 2 秒预算约束，下一步若需提高追赶速率，应独立测量维护门控后的有效吞吐和并行预读对导入/查询的影响，再决定调整预算。

仍需针对约 128k 次小读做有界合并或目录批量预取，并以相同路由覆盖的固定输入复测，而不是继续增加跨请求无界缓存。目标应同时减少应用读取字节和系统调用，随后再检查 35M 的实际命中读取；仅消除解码不足以解决缓存不足时几十秒的首查。本轮没有为这些后续候选再次修改产品源码。
