## 为什么块数相近，字节却增多

| 成功写入 pack 的平均值 | 部署后首窗 | 当前 6 分钟 |
|---|---:|---:|
| 已编码字节/pack | 241,300 B | 1,355,796 B |
| 变化行/pack | 448.36 | 556.43 |
| 已编码字节/变化行 | 538.18 B | 2,436.59 B |

当前行数/pack 增加约 24%，编码体积/行增加约 353%；体积增长不能只由交易数解释。
本窗 pack 写入 6,239,373,444 已编码字节，未压缩 11,518,787,025 字节，编码后约为
未压缩的 54.17%，压缩仍在工作。

独立的每 128 行采样中，Prev 旧值载荷平均 4,521 B/采样行，占单行未压缩编码
99.04%。Next 本来就未持久化，不能再作为待删冗余计算。现有指标无 domain 标签和
大小直方图，尚不能定位到 account、某一合约 KV 或少数异常大值。

pack 计数在成功 Put 后增加，可能对应 buffer/batch，存在重试；与唯一 canonical 块
和当前保留库存不同。全局行采样发生在 Put 之前，两个采样总体也不同。不能用当前
每 pack 字节乘 347,214，计算精确热历史占用。

## 压实与后续定位重点

17:24 的补充检查先读取同一进程的清理水位 **H=30,062,491**，约 0.18 秒后只读
复制当前 MANIFEST；复制 34,809,466 字节，约 0.15 秒完成，解析约 5 秒。
selector/inode 未变、复制期间无追加、70,649 个完整记录、clean EOF，无遗漏尾部。
探针未另开 Pebble DB、未扫描 SST 内容，只重放元数据中的当前版本。

|---|---:|---:|

| 全部不高于 H | 523 | 16.295 |

本次无混合 namespace 的 L6 表；其余 namespace 占 100.960 GiB，所有分类字节和
表数与 L6 总计一致。**93.18% 的分母是 L6 changeset 表字节，不是整个 chaindata**。
不高于 H 与跨 H 的表合计至多 16.326 GiB，可见低于清理水位的 L6 changeset 文件
不是当前主要占用。这个结果与新增 pack 增密一致，比仅依据 L6 总量猜测更有区分力。
但 >H 仍可能含同键旧版本，≤H 也不等于可回收量；未覆盖 L0–L5，更不能单独解释
过去 7 小时每一时刻的增长因果。

第一次检查使用 16:59 的固定 H=30,031,466，随后以现场水位补查消除约 25 分钟的
水位时差。两次均只读成功，09:24:35 UTC 服务身份和原配置末检通过。
原始服务器证据位于 `/data/gtron/reclaim-diagnostics/20260913-manifest-probe/`，
最终采用 `result-02-near-height/capture.json`、`manifest-analysis.json` 及
`near-capture-metrics.json`；本地为截图人工转录，不能冒充原始 stdout。

临时探针的 3 项 Go、2 项 Python 离线测试及独立复核通过，包含 CRC 合法但语义
截断导致工具打印 EOF 的拒绝用例。独立目录原生构建并生成模块校验文件，源数据库
和生产模块文件均未修改。长行命令在发送前改为分段并逐段校验；实际执行通过整体
SHA256 后才解包，未执行未通过校验的包。任务专用 SSH 已退出。

压实持续运行。范围删除提交的是 range tombstone，物理旧内容要到相应 SST 被压实
才可回收；L6 的部分 elision 工作优先级低于普通层级压实，没有固定完成时间。
本窗 L6 压实读入 3.636 GiB、写出 0.920 GiB，同时 L6 文件总量仍从 322.739 GiB
增至 325.250 GiB。跨约 7 小时 L6 也有 193.401 GiB 读入、61.906 GiB 写出；
有压实活动与数据库仍增长可以同时发生，处理流量不是释放空间。
末点 snapshots/zombies 为 0，窗口内短暂达到 4 个 snapshots、0.316 GiB zombie SST；
这些观测不能排除旧记录仍留在当前 SST 内。

Posting 清理本窗 callbacks/chunks 仍为 0。13 个采样点的压实债务均高于其 32 GiB
准入门限，足以拒绝准入；现有指标未拆分每次轮询的压力原因。
state_change_index 估算包含 posting 和 key 目录，
不能把约 45.45 GiB 都视作可删除 posting；其增长也不是本轮最大来源。

本轮已经按清理水位区分了 L6 的文件高度范围。下一步优先对 Prev 的 domain 和
大小分布做有界观测，定位保留范围内的历史体积来源；再依据字节量、实际回收和
同步影响决定编码、保留与范围回收调度，保留规则变化需先核对历史查询正确性。
posting 的持续压力门限需单独评估有界工作预算。不能仅提高压实并发或以全库压实
替代归因，也不应承诺清理水位前进后磁盘立即下降。

当前删除字节指标没有覆盖旧 point fallback 的 value 字节，不能用“pack 写入字节
减 range/point 指标字节”推算净活数据或已释放空间。
