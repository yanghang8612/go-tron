固定 9M 完整 HTTP `eth_call` 的中位数：暖缓存 **157.744 → 128.202 ms（减少 18.73%）**，新进程 OS 缓存未控制 **187.561 → 162.179 ms（减少 13.53%）**，独立副本 OS 冷缓存 **784.103 → 759.823 ms（减少 3.10%）**。154 个返回值全部正确。改善主要来自 CPU，冷读收益仍小，不能承诺消除秒级尾延迟或代表所有合约、生产 p95。

最终候选冻结为 `43c3d47bc1229223af677ff4c56462744cf54631`，包含 `e547e830` 的 owner/行范围索引和 `4693a154` 的 posting 水位回收。基线是上一轮离线候选 `4d34e751`，不是当前生产二进制的直接 A/B。本线程未推送、部署、停止或启动生产服务，未删除/重置生产库，也未恢复定时任务。运行期间观察到独立的生产停机，详见下面的时间和隔离说明。

## 最终实现

新增 schema 管理的可选 `state-change-owner-spans-v1-` 派生键，索引体版本 magic 为 **GTHOS002**。每块索引包含完整 21 字节 owner 字典、连续同 owner 行在原 RLP 列表中的字节范围/行数/首 sequence、解码尺寸，以及 exact encoded 原包的 **BLAKE2b-256**。整个有界索引另有 BLAKE2b-256 checksum。范围完整分割原行列表，禁止洞、重叠和 sequence 溢出。

仍完整读取、解压并按原算法认证 canonical raw/Snappy/v2/v3 包及引用 chunk；仅跳过无关 owner 行的字段解码。规范历史字节、共享 chunk、共识哈希、MuHash 输入和原有 SHA 算法均不变。辅助摘要不是共识哈希；旧 GTHOS001 索引体退回普通读取，可以重建。

选中行先完成全范围的 owner、sequence、边界、行数和 TxNum 顺序校验，再执行回调；缺失、过期、损坏、过密或超预算索引无部分回调地回退。原始包/chunk 错误仍硬失败，不能转成“没有数据”。正 sequence repair 仍先覆盖 packed sequence，再筛 owner。只用于 pinned view，没有跨视图的认证数据缓存；pool 只复用受限 scratch 容量，每次重验当前字节及源。

只有明确声明 block 原子写能力的写入器才与原包同批发布索引。辅助 metadata 上限 4 MiB / 65,536 owners/runs；源至少 16 KiB、32 行、两个 owner，平均行不超过 4 KiB。encoded 大于 raw 一半不建索引；辅助值不超过 4 KiB 加 encoded 一半；读时选中行超过三分之一则回退。离线构建固定源、严格检查所有原行，只允许写指定尾部内的辅助键。

索引路由至 direct history，并随对应原始块清理；posting 水位推进时更早在同一 history batch 回收已覆盖索引。大推进用一个 prefix 内范围删除，小推进/无进展轮次每次至多 512 个点键和 4 MiB 加一个完整值，反复扫 prefix 捕获延迟 flush 的旧辅助写入。旧 MVCC 保持可读，辅助索引不能推进规范水位。单块/维护预算不等于全库恒定空间；长期占用仍取决于未索引尾部长度。

## 实验迭代

早期 raw SHA 原型在 microbench 中变慢，改用 exact encoded 源及 scratch 复用；两者 fixture 不同，不能跨文件比较比值。首次过宽服务器构建还误覆盖了已建立 posting 的冷化积压：358.17 秒时遍历 329,970 包、建立 323,435 索引，增加 1,398,781,282 B 辅助逻辑键值。主动停止自己的离线试验，保留副本/回执；该试验没有完成 HTTP、全量 MuHash 或恢复验收。

随后只为 **11,817,531..11,818,192，共 662 块**未索引尾部建索引，并补齐 posting 水位回收。SHA256 版本 `4693a154` 的完整 HTTP、全量 MuHash 和恢复都正确，但 9M 暖只快 7.25%，OS 冷反慢 3.41%。20 秒行级 CPU profile 中，新源 SHA 校验占 20.25%、辅助 checksum 占 5.61%，抵消了很多字段解码收益。

服务器 4 KiB..1 MiB 摘要微基准中，BLAKE2b-256 约用 SHA256 四成耗时，因此最终仅更换辅助摘要，保持规范算法不变，再完整复测。SHA 原型的全部验收及失败成本见 [独立试验报告](history-owner-spans-sha-trial-20261021.md)。两轮服务器背景负载不同，不把跨轮下降当作精确消融收益；最终结论只用本轮内部交错 A/B。

## 空间与写入成本

662 包全部建立并逐包严格重建核对：**379,603 行、322,442 个 run、80,155 个 owner 字典项**。System 与测试合约共 **3,083 行（0.8122%）**。索引逻辑键值 **2,718,757 B**（值 2,694,925 B），相当于解码原包 32,117,941 B 的 **8.46%**、编码 changeset 键值 11,255,555 B 的 **24.15%**。构建 **0.203 s**，含严格核对 **0.438 s**；温热尾部不能用来估计全盘 backfill 时长。

新私有 history 文件长度合计 **6,678,772 B**、allocated **40,886,272 B**，包含 WAL 恢复、预分配和 metadata，不能全部归因于辅助索引，也不是服务器净磁盘增量；副本及旧库仍保留。

24 个真实块（341..670 行），每块两模式各四轮 AB/BA、每轮 30 次内存 batch 回放，dedup/shared 两臂均关闭。24 块中位耗时之和 **7.801 → 11.229 ms**，增加 **43.94%**，平均额外 **0.143 ms/块**；逐块相对开销中位数 **45.58%**。batch 逻辑字节合计 **386,628 → 479,541 B**。这是隔离写入器，不包括完整执行、持久化、共享去重及同步并发，不能解释成完整同步慢 43.94%，也不能证明同步完全无损。

## 剩余成本

9M 主比较：暖 CPU **157.182 → 129.511 ms**，分配 **18.028 → 24.136 MB**；OS 冷 CPU **225.193 → 195.961 ms**，分配 **25.492 → 31.931 MB**。query syscr 仍为暖 **165**、冷 **1,871**，rchar 仍约暖 **6.368 MB**、冷 **22.679 MB**。降低 CPU 的同时新增 metadata 查找/解码分配，物理读取几乎未减少。

排除于主计时的单次 OS 冷 strace 请求为 **938.094 ms**。请求窗口成功归属 1,869 次 read/pread，另有 42 行未解析，原记录保留。hot history SST 占 **1,669 次、14,685,371 B**，系统调用耗时和 **0.546260 s**；冷 history 的 `.seg` 为 59 次 / 1,325,060 B，`.kv` 为 95 次 / 316,616 B，`.route` 为 9 次 / 4,726,295 B。调用时间可跨线程重叠，不能加总成互斥的墙钟百分比；strace 本身也有开销，不能替换主比较中位数。

20.12 秒 CPU profile 共采样 20.22 CPU 秒、159 个正确调用。热尾路径累计 **48.37%**，其中 owner spans **45.30%**；原包 Snappy 解码累计约 **18.55%**，源辅助 BLAKE 校验 **10.34%**，辅助索引解码 **8.01%**（含 checksum **2.77%**）。这些累计成本有包含关系。全栈 Snappy Decode 为 19.29%，SHA Digest.Write 为 15.53%，BLAKE Sum256 为 13.06%；规范 SHA 仍保持原有语义，没有为性能跳过认证。冷 history FirstStateDomainChangesContext 累计 30.76%，latestSegmentRef 11.28%，仍有独立优化空间。源码行级 profile 与原始 profile 一并保留。

下一步应优先减少热尾的**实际读取/解压范围**：将 owner 行分成可独立定位、独立验证的有界 frame，或在 pinned 请求内合并/预取连续 history SST 读取。现有范围索引只跳过字段解码，仍读取并解压整包，因此不能单靠继续压缩 metadata 解决 OS 冷延迟。另可减少 metadata 解码分配，以及复用请求内 System routing/latest 定位；需要继续保留源错误硬失败、MVCC 和恢复顺序的独立对照。本轮尚未实施这些后续格式/读取改动。

最终恢复执行阶段采集 **138** 个资源样本，MemAvailable 最低 **43.87 GiB**，各阶段 cgroup 峰值最高 **3,884.76 MiB**；均限制 CPU 200%、内存 5 GiB，阶段串行。原准备/失败恢复样本也保留在同一资源文件中，不能把旧 failed 状态当作最终阶段失败。最终自己的离线阶段均结束，旧失败 transient units 仅 reset-failed，没有启动生产服务。
