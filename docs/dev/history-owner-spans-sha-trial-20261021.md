# 首次热尾 owner/行范围索引验证（2026-10-21）

本轮索引使固定 9M `eth_call` 的暖缓存中位数由 **165.290 ms 降到 153.311 ms（减少 7.25%）**，但新进程基本持平，私有 OS 冷缓存由 **824.982 ms 变为 853.081 ms（慢 3.41%）**。因此结果是有限的暖 CPU 收益，尚未证明冷查询加速，不能据此推荐上线或承诺消除秒级尾延迟。

候选源码冻结于 `4693a15485cbc0db810e331d21aab418baf22e38`（索引实现 `e547e830`，posting 水位回收 `4693a154`），基线为上一轮 `4d34e751`。未推送、部署、重启生产，也未删除或重置生产数据，未恢复定时任务。

## 实现及边界

增加 schema 管理的可选 `state-change-owner-spans-v1-` 派生键。每块索引含完整 21 字节 owner 字典、同 owner 连续行的 RLP 字节范围及行数、首 sequence、解码尺寸、**原编码包 SHA256**；有界索引本身另有完整 checksum。范围必须完整分割原行列表，不能有洞、重叠或 sequence 溢出。仍按原路径读取、解压、认证 canonical raw/Snappy/v2/v3 包及引用 chunk；减少的是无关 owner 行的字段解码，未实现 Snappy 内部随机解压。

选中行先完成所有范围的 owner、sequence、边界、行数及 TxNum 顺序验证，再执行回调。缺失、损坏、过期、过密或超预算索引退回原读取器；原始包或 chunk 错误仍硬失败。正 sequence repair 仍覆盖原 packed sequence 后再筛 owner。必须使用 pinned view，没有跨视图的已认证数据缓存；pool 仅保存受限 scratch 容量，当前索引和源每次重验。

只有明确声明原子 block 写能力的写入器才同批发布原包和索引；离线构建器固定源视图、严格解码所有原行，只能写范围内辅助键。metadata 上限 4 MiB、65,536 owner/run、原包至少 16 KiB/32 行/两个 owner，平均行不超过 4 KiB。encoded 大于 raw 一半不建索引；辅助值不能大于 4 KiB 加 encoded 一半。选中行超过原包三分之一则读时回退。

索引路由到 direct history，随对应原始块清理；更早在 posting 水位发布的同一 history batch 回收已覆盖索引。大推进使用单个 prefix 内 DeleteRange，小推进/无进展轮次每次至多 512 个点键和 4 MiB 加一个完整值，并反复扫 prefix 捕获延迟 flush 的旧写入。不会改变 canonical/history/MuHash、发布或清理水位；旧 MVCC 保持可读。回收缺失索引后原查询路径仍完整。

## 失败试验与范围修正

早期 raw SHA 原型在 microbench 中反而变慢，后改为绑定 exact encoded 源，并对解码 scratch 复用。原型与最终 microbench fixture 不同，不跨文件比较比值，也不把 microbench 当作完整 HTTP 结果。

第一次服务器构建误覆盖所有仍热存的旧包，包括已建立 posting 的冷化积压。358.17 秒时已遍历 329,970 包、建立 323,435 索引、写出 **1,398,781,282 B** 辅助逻辑键值，主动停止本轮自己的离线单元，保留副本和停止回执。该试验没有完成 HTTP/MuHash/恢复，不能计作验收。随后限定到真正未索引的 **11,817,531..11,818,192，共 662 块**，并增加 posting 水位回收。

## 固定副本与完整 HTTP 对照

沿用 HEAD **11,818,192**、TxNum **601,386,177** 的同一规范捕获及上一轮 V2 冷路由。两臂均读取**同一最终 indexed 物理输入**，基线忽略未知可选索引，排除不同 WAL 恢复、SST 布局造成的对照偏差。原输入 SST/冷文件 inode、长度及冷 metadata 摘要复核不变，索引写入只允许辅助键及尾部范围；该范围原 changeset/tx-range 和相关 chunk 桶前后摘要一致。此尾部没有 shared chunk 条目，不能将它表述为真实 v3 chunk 压力测试；共享包语义另由单元测试覆盖。

合约 `0xa4997124a328a4615eab437cede31da47a31b375`，data `0x9fa6a6e3`，省略 from、value=0；七高度期望值为 **6、7、63、207、225、225、225**。相同 SHA256 的完整 HTTP host 走 loopback HTTP → JSON-RPC handler → TronBackend → TVM → JSON；oracle 是完整规范历史 before-image 折叠，与 fast seek/cache 独立但共享底层 codec。

共 **154 个返回值全部一致、112 个主计时样本**。每高度每版本暖缓存 n=4，AB/BA；新进程 OS 未控制 n=2；独立 inode OS 冷 n=2。只对观测并证明私有的读取集 fadvise DONTNEED，mincore <1%；没有全机 drop_caches，也不声称设备冷缓存、生产负载或 p95。GOMAXPROCS=2、GOMEMLIMIT=3 GiB、hot/history 各 512 MiB、latest 128 MiB；没有 importer/P2P/冷化/清理并发。

## 索引空间和写入成本

662 包全部建立并逐包严格重建核对，**379,603 行、322,442 个连续 run、80,155 个 owner 字典项**。System+计数合约共 **3,083 行（0.8122%）**。索引逻辑键值 **2,718,757 B**，其中值 **2,694,925 B**；相当于 32,117,941 B 原解码包的 **8.46%**，或 11,255,555 B 原编码 changeset 键值的 **24.15%**。构建 **0.260 s**，含严格校验 **0.526 s**；包含 writer replay 的测试共约 3.97 s。读取到的温热源不能用来估计生产全盘 backfill 时长。

新私有 history 文件长度合计 **6,678,772 B**、allocated **40,886,272 B**，包含 WAL 恢复、预分配和 metadata，不能全部归因于索引，也不是服务器净磁盘增量；旧副本仍保留。

24 个均匀选取的真实块（341..670 行），每块两模式各四轮 AB/BA、每轮 30 次内存 batch 回放，dedup/shared 两臂都关闭。24 块中位耗时之和由 **8.392 ms** 增至 **13.478 ms**，增加 **60.61%**，平均额外 **0.212 ms/块**；逐块相对开销中位数 **58.55%**。batch 逻辑字节合计 **386,628 → 479,541 B**。这隔离的是存储写入器，不包括完整执行、持久化、共享去重或同步并发；不能解释为完整同步慢 60.61%，也没有据此声称同步速度不受影响。

## 正确性验收

本地及 Linux/Go1.25.5/Sapling 的 rawdb/state/snapshots 完整包测试、针对性 race（含 index stage）、core/CLI 的 StateHistoryIndex、MuHash、ArchiveQuery、快照/恢复回归、vet 和构建均通过。服务器二进制与源码清单绑定；最终原始证据另在本地复核。

候选在最终 indexed 固定副本全量重算 MuHash，耗时 **893.02 s**。状态源三族 **3,484,117 / 481 / 141,418,493 行**，合计 **144,903,091 行**；根与固定捕获一致。三个真实主网历史窗口（3,144,020、5M、9M 起各 20 块）实际恢复 **387 / 11,845 / 10,264 行**，合计 **22,496 行、60 条交易范围**。完整参考、候选读取及恢复后的全行 SHA256 一致。恢复适配器用独立核对的 StateTxRange 补全 rawdb 省略的 BlockHash，另有 CLI/单元快照恢复回归；没有声称穷举导出再导入全部 11.8M 历史。

固定 MuHash 为 `8fbf149684146a59b1650b318a768f0edbae0c8c1c3ceb2c5c610129c10f76a5`，区块哈希为 `0000000000b454d09a46886a40d09d8cbec73812d013f57de1fc803784acfdf6`。

## 剩余瓶颈与后续实验

9M 暖 CPU 中位数 164.322 → 152.700 ms，分配 18.033 → 24.140 MB；OS 冷 CPU 238.695 → 245.003 ms，分配 25.458 → 31.655 MB。两版本 query syscr 一致（暖 165 / 冷 1,871），rchar 基本一致（暖 6.368 MB / 冷 22.679 MB）。辅助索引没有减少整包和 SST 的首次读取。

独立私有 OS 冷 strace 返回 207，耗时 **1,023.191 ms**，排除主比较。热 history SST 仍 **1,668 次 / 14,683,281 B**，累计 syscall elapsed **0.573558 s**；冷 `.kv` 95 次、`.seg` 59 次。不同线程 elapsed 可以重叠，不能相加当作 wall time。

20 秒暖 CPU profile 中，owner spans 累计 53.35%，其中原包 SHA256 行 20.25%、索引 checksum 行 5.61%；`decodeHistoryOwnerSpansInto` 累计 10.57%（包含 checksum），Snappy Decode 16.77%，latestSegmentRef 9.68%。比例相互包含。行级剖析由原始 profile 和精确源码在本地重新渲染；索引确实跳过了无关行字段解码，但新摘要成本抵消了很大一部分收益。

因此该 SHA 原型不建议直接部署。继续在下一轮验证仅用于辅助索引的 BLAKE2b-256，同时保留规范历史、共识哈希和 MuHash 原算法；整个 HTTP、MuHash 和恢复会在下一候选重新验收。进一步降低 OS 冷延迟还需要 owner 独立帧或物理范围读取，当前整包读取保留这一限制。

完整证据 ZIP **2,644,478 B**、**288 文件 / 18,695,017 B** 原始条目，SHA256 `20009df52574cf5eb180f7a66a8ab570c20cc03f4ba07d1e8542d420d73e8ae6`。正常 SFTP 下载后复核 ZIP CRC、每条目摘要、1074 个候选/1073 个基线 Git blob、逐请求与所有中位数、原始 trace、MuHash 源摘要和恢复回执，通过。证据位于 [SHA 试验目录](evidence/20261021-hot-owner-spans-sha-trial/README.md)。
