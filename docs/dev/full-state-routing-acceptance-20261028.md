本轮优化在同一固定副本上有明显收益：9M 完整 HTTP eth_call 热查中位数从 **16.4135 秒降至 2.0020 秒（8.20 倍）**，新进程首查从 **76.7462 秒降至 3.1394 秒**。35M 热查从 **13.5746 秒降至 3.0488 秒**。候选仍有约 2 秒 CPU 消耗，没有达到毫秒级深历史查询。

“首查”准确含义为新进程、操作系统文件页缓存未控制；不能称为完全冷缓存。热查也不保证基线没有物理读。9M 基线热查实际范围 10.7663–56.8558 秒，候选 1.9525–2.1006 秒；基线波动较大。样本量只适合中位数/范围，不计算 p95。不能把此处倍数直接套用到此前不同切点、不同负载的线上 43.8 秒。

接近切点的行为变化小：H−1 热查增加约 9.94 毫秒（约 5.1%），现有四个热样本不足以判断稳定回退；H−256 基本持平。深历史五个点都明显改善。latest 数毫秒的差异不应解读为有意义的优化倍数。

两版均使用真实 TronBackend、JSON-RPC Handler、原生 Sapling 链接库及相同 HTTP 测试宿主，打开完整只读状态/history/ancient，没有 P2P、导入、冷发布或清理。完整 loopback HTTP 时延包含序列化、网络和服务端执行；CPU/heap 剖析在正式 96 次样本之后单独执行，不混入计时。

资源统一为 CPUQuota=200%、GOMAXPROCS=2、GOMEMLIMIT=4GiB、systemd MemoryLimit=8GiB、Nice=19；hot/history 各 512 MiB，manifest 预算 512 MiB，latest cache 128 MiB。生产 hot cache 为 12 GiB，且有同步/冷化负载，不能将隔离结果当作线上绝对 SLA。

候选热查墙钟时间约等于 CPU 时间，且没有物理读，说明该组剩余延迟主要是 CPU 工作，继续单纯调大磁盘缓存不能消除这约 2 秒。

独立 30 秒 profile 共 24.80 CPU 秒，期间 12 次 getter 全部返回 207。带 eth_call 标签的累计采样中，热 history materialized block 路径占总采样的 32.70%，冷域批量查找占 31.94%；行解码 16.85%，Snappy decode 13.51%，SHA256 flat 13.99%。这些累计路径存在包含关系，不能相加。堆内存约 1,136 MiB，其中 ancient 交易索引启动保留约 739 MiB，不是每次调用的额外开销。

SHA256 调用树进一步定位：大系统路由读取路径仍约 2.50 CPU 秒/整段 profile，manifest pair 身份等批量查找哈希约 1.53 秒；轻量系统路由和 metadata 页哈希各约 0.05 秒。后续优先方向是：

1. 热尾按 owner/行范围合并读取，每个键保留自己的冷段边界，减少重复解压和 RLP 扫描；保留取消、同交易多次变化与删除语义。
2. 在不可变 manifest 上复用 pairID、latest ref 索引，减少每个请求重复计算和线性定位。
3. 大路由使用有认证的分页读取及请求内共享，缩小读取/哈希范围；不能仅凭 inode/mtime 代替内容真实性校验。

本轮没有为上述下一步再改产品代码，以免延迟性能结论或混用版本。
