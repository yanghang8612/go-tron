## 异常项与优化顺序

**先定位 4 次代码哈希校验拒绝。** `state/code_strict/errors` 与 `state/code_cache/hash_rejections` 均从部署初期的 0 变为 4，在 14:01–14:13 的采样中没有新增。现有日志没有对应事件上下文。源码显示严格读取会拒绝哈希不匹配的数据，但指标无法确定调用来自主链执行、查询还是影子执行；这既不能直接证明主链数据损坏，也不能忽略。下一步宜补充限量、结构化的调用来源、合约地址、期望/实际哈希和高度记录，再针对事件回放；保留现有校验。

影子执行拒绝计数亦有增长：首次部署后采样至末点 sender_chain/errors 增加 879，VM sender_chain/errors 增加 941，其中 readiness 809、apply_unsupported 62、result 70；sender_retry/errors 与其 async_actual/errors 均增加 1，属于嵌套统计。它们不是可直接相加的主链失败数。观测到的冷存储、commitment、prune、freezer 错误计数没有新增。

建议按以下顺序开展性能工作，并用相同历史区块回放验证：

1. **先让归档具备稳定净追赶能力。** 核实历史预算的工作/恢复时间、探针未知状态与 event parallel 利用率，分开记录构建、合并和等待时间；在保留内存、磁盘保护的前提下试验恢复间隔和探针刷新方式。验收以持续窗口内状态发布高于导入、额外积压下降，同时前台吞吐和读延迟不恶化为准。同步记录每导入块的 SST 读写量、各层压缩量及延迟，判断压缩与历史构建之间的干扰。
2. **减少前台 SLOAD 的持久化点查。** 按 ContractStorage 等域以及容量/版本失效原因拆分 cache miss；对比存储专用预算或准入策略。涉及 `core/state/statedb.go`、`core/blockbuffer/buffer.go`。必须保持 dirty overlay 优先、存在零值与缺失的区别、账户 generation、版本绑定和读集记录。
3. **减少 commitment 深层父分支重复读取。** 先分辨深度 6/7 的容量失效和版本失效，再试验按 snapshot 版本保留/共享分支缓存。涉及 `core/blockbuffer/layer_view.go`、`base_read_cache.go` 和 `core/state/domains/commitment_staged.go`。保留父快照可见性、tombstone/frozen fallback 和借用内存生命周期，继续衡量预取实际收益。
