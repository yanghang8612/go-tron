# 未覆盖冷尾点查读取优化（2026-10-28）

本轮基于 `cda883ba`，仅推送 `codex/routing-bootstrap-20261028` 用于源码传输；不修改 master，不部署、不重启或删除生产数据。最终保留 `80293e10` 的有界有序并行读取及头尾合并。随后测试的随机读取提示 `9365e067` 和 32 源窗口 `27e4e4aa` 均未保留；收尾提交 `be673f33` 的 core 产品源码与 `80293e10` 完全相同。

## 改动

`FirstStateDomainChangesContext` 在同一固定 manifest 上按原有路由规则选择源。最多预读 8 个独立 history/accessor 对，进程级准入同样限制为 8 对。工作线程只读不可变数据，查询状态仍由请求线程按 manifest 顺序更新。已被更早结果满足的键不会暴露后续投机读取的错误；部分键已满足时仅重读仍需要的键。单任务最多保留 1 MiB 结果，超限回到原串行回调路径。请求结束先取消并等待所有工作线程关闭描述符。

accessor 的 magic 与头部共用同一物理页缓存；倒序访问的相邻 footer 共享 EOF 最后一页。缓存和已解码目录仍限定在当前描述符/批次，不跨请求借用认证结果。CRC、字典绑定、代次、范围与行匹配检查保留。

试验候选曾仅在精确键读取的 Linux 描述符上调用 `FADV_RANDOM`，但本轮不保留该提示，原因见下表；保留版本仍使用普通内核预读。

## 固定输入和测量

同一 H=45,836,827、Tx=4,240,407,293、MuHash root=`4bb19b7a938ba6c865820ea86f5239235172f84923c350b04c4b0eb75743b627` 副本。主对照使用上一轮出现 69.477 秒首查的 `candidate-maintenance-input`，small 覆盖 25,656 / 32,036 源，metadata 覆盖 768 源。没有补建路由或改写 canonical 数据；已有完整路由是另一组对照。

同一个完整 loopback HTTP 宿主、同样 2 CPU、GOMAXPROCS=2、GOMEMLIMIT=4GiB、MemoryLimit=8GiB、hot/history 各 512MiB。调用合约 `0xa4997124a328a4615eab437cede31da47a31b375`，calldata `0x9fa6a6e3`；9M 结果逐次核对 207，35M 与近 HEAD 对同切点基线值。

首轮 35 次矩阵使用新进程和后续调用，不清共享页缓存，不能把这种首查称为受控 OS-cold，也不能直接用 70.9→5.3 秒算优化倍数。

为比较冷尾，另用 IN_ACCESS 发现实际读取的冷文件，创建独立 inode 的私有副本；复用已完成的约 42.0 GB 私有文件，新增约 91.8 GB，共 12,995 文件、133,808,033,713 B。复制记录字节数与不可变源 inode/size/mtime，查询时保留引擎校验，不额外全文件重哈希。每次冷调用前仅对私有文件执行 fadvise DONTNEED，并用 mincore 核对零驻留页，再检查该次实际读取是否全部包含在控制集合中。没有全机 drop_caches，也不驱逐生产或共享源 inode。

这组冷缓存的范围是冷库文件页；进程启动缓存及 hot Pebble 缓存保留，并非整机/整个服务完全冷启动。冷尾范围相同，HTTP 端到端计时相同，三版本分别记录，不混用不同路由覆盖。

## 验证

本地相关测试通过（20.865 秒），有序结果/错误、取消等待、超限回退、混合业务键和页读取的 race 通过（最终 5.351 秒），vet 通过；随机提示后的相关本地测试通过（2.858 秒）。原生相关测试通过（1.505 秒）；提示试验与大窗口试验的原生相关测试也通过（1.561 / 1.818 秒）。本地已逐项验证 110 个封存文件、65 次正式 HTTP 返回及服务端资源计数、8 次受控冷页驻留与实际读取覆盖。另有 3 次读取集发现查询不计入正式矩阵。

本轮没有重复十亿行 MuHash 或完整快照导出恢复。格式、canonical rows、MuHash 元素及发布/清理前沿不变；各 HTTP 宿主核对同一 HEAD/hash/Tx/root。本结论是只读查询优化，不能冒充新的完整写入/恢复验收。

## 性能结果

同一不完整路由输入、同一资源限额，第一轮按 B/N/N/B 交错：

| 9M 完整 HTTP eth_call | 旧读法 | 保留方案 |
| --- | ---: | ---: |
| 受控冷库文件页，逐次耗时 | 69.848 / 68.382 s | 23.443 / 21.153 s |
| 冷页中位数（各 n=2） | 69.115 s | 22.298 s |
| 冷页进程 CPU 中位数 | 9.890 s | 10.904 s |
| 冷页累计分配中位数 | 1.857 GB | 1.903 GB |
| 冷页进程读盘增量中位数 | 2.295 GB | 2.298 GB |
| 冷页读取系统调用中位数 | 130,373.5 | 123,761 |
| 同阶段宿主峰值 RSS | 2.496 GiB | 2.485 GiB |

相同交错阶段的冷页时延减少 **67.74%**，约 **3.10 倍**；它不是 p95 或并发 QPS 结论。第二轮独立的提示对照中，普通内核预读的保留方案又测得 20.955 / 19.775 秒；这两次属于另一阶段，单列保留，不拿它们替换第一轮基线来放大收益。

保留方案主要重叠了独立源的等待，并没有把读取量一起降下去：进程 CPU 约增 10.3%，累计分配约增 2.5%，读取调用减少约 5.1%，应用读取从 867 MB 增到 920 MB。增量包含页合并的有限过取及有界投机；进程读盘量约 2.3 GB，基本不变。上述 counter 来自进程差值，包含该进程所有工作线程；CPU 可大于墙钟，分配量不等于常驻内存。

普通矩阵中只取后续调用且 `read_bytes == 0` 的 9M 样本，旧读法 4.479 / 4.491 秒（中位数 4.485，n=2），保留方案 3.920 / 3.726 / 3.744 / 3.674 秒（中位数 3.735，n=4），时延约减少 16.72%。CPU 中位数 4.639→5.021 秒、分配约 1.675→1.720 GB，说明热查收益也来自有限并行，而非全部 CPU 工作量减少。冷页阶段的后续零读盘样本为 3.757 / 3.678 秒，第二阶段另有 3.800 秒。旧读法最后一次“第二次调用”耗时 57.317 秒，实际仍读盘 2.520 GB；该样本原样保留，不能混入真正的零读盘热组。

其他高度的后续调用：35M 旧读法 5.652 / 5.737 秒，保留方案 4.432 / 4.213 秒；接近 HEAD 的 45,836,826 分别为 0.296 / 0.235 秒和 0.195 / 0.316 秒。近 HEAD 存在波动，本轮没有足够样本证明稳定改善或排除小幅回归。

已有完整路由的保留方案，9M 后续调用为 2.070 / 2.028 秒，累计分配约 300 MB、应用读取约 90 MB、读取调用约 1,963 次；35M 后续为 2.621 秒，近 HEAD 0.210 秒。它与不完整路由组覆盖不同，不能当作本次回退读取器本身的提速倍数。

## 两个未保留试验

`FADV_RANDOM` 按 R/N/N/R 交错，普通 8 源方案冷页 20.955 / 19.775 秒，随机提示为 22.628 / 23.482 秒；提示组中位数反而慢约 13.21%。实际读盘中位数从 2.282 GB 降到 0.991 GB（减少约 56.57%），读取调用仍为 123,761 次，但没有换来目标延迟改善。本轮优先延迟，故不保留这个全点查随机提示；数据量减少本身不能当成延迟优化已经生效。

32 源窗口通过原生相关测试及一次完整 9M 发现查询（返回 207），但发现的额外读取文件集合超过 512 MiB 私有复制预算，试验按预设成本上限停止。没有再次扩大复制、没有受控冷页 32 源结果；不能据此声称 32 源一定更慢或更快。保留经过完整冷热对照的 8 源窗口。

提示试验最初两次因驱动名 `random.py` 遮蔽标准库导致循环导入，均在发出 HTTP 前失败；原始失败状态和空服务端请求文件保留。修正文件名并预检标准库路径后，复用已构建的同一原生二进制续跑，没有重建库或重做文件复制。

## 余下瓶颈与结论边界

9M 首查已由约 69 秒降到约 20–23 秒，仍是秒级慢查询。冷查询涉及 6,496 个 accessor 和 6,496 个 history 文件，另有 3 个路由文件；每次仍有约 12.4 万次读调用、920 MB 应用读取，8 源并行无法消除这些权威存在性探测。完整路由对照约 2 秒也说明，减少需要探测的源比继续盲目扩大并发更有价值。

下一步应细分未命中源的头尾/目录认证读取链，寻找可以省掉或合并的读取，并推进既有轻量路由与 metadata 覆盖。当前数据不能把剩余成本全部精确归给单一 footer 解码函数；本轮没有再采候选 CPU 栈，保留这条归因边界。热组 CPU 与分配仍有成本，当前并行结果不等于压缩解码本身已变轻。
