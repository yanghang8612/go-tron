# 系统键独立冷历史路由：离线验收

独立系统键路由已实现，并覆盖固定大目录全部 27,893 个冷源。60 个系统键加一个不存在键的批查询，无跟踪热缓存中位数从 1.451 秒降至 228 毫秒；完整 HTTP 的 9M 冷缓存仍未证明收益，不能宣称秒级问题已全面解决。

本轮只修改辅助查询路由及维护、校验、退休逻辑。生产服务保持原二进制和现有数据库，未推送、部署、重启或删库。

系统/零账户和 generation 键，以及系统 owner 的 DynamicProperty、ForkVote 键使用独立 `small-system-history-routing`。键从经过认证的源字典动态发现，59 不是硬编码名单。ContractStorage 和 ContractMetadata 保留原路由。未覆盖源按原始读取器查询；覆盖绑定完整 history/accessor 身份，范围相同的替换段不能继承旧证明。

首次为旧库启用时，尚未生成或尚未覆盖的源会走原始读取器，正确性保持一致，性能不能假定等同于已全覆盖的测量。维护单次最多尝试 64 个源，发布安排必须计入回填成本；本轮没有把离线生成的路由写入生产目录。新增 manifest kind 需要相应新读者，旧读者不支持该辅助类型。

轻量路由单独缓存。跨请求缓存命中也重新读取、校验当前物理文件。导入时逐源重建成员集合，拒绝校验和正确但遗漏成员的伪造索引。维护最多尝试 64 个新源，独立游标避免前面的不支持源使后面的源永远轮不到；游标本身不表示覆盖。64 MiB 是工作集/缓存计费预算，不能当成 RSS 峰值。

## 固定副本的完整 HTTP

基线源码 `d11f4a57fa327c468294ee133ae8a78ac9fe0dda`；候选查询代码的逐文件 SHA256 与本地修改核对。服务器使用 Go 1.25.5、Sapling 构建。两版均固定在 11,818,192 高度、601,386,177 TxNum，使用相同 canonical 数据和资源预算：GOMAXPROCS=2、GOMEMLIMIT=3GiB、测试单元 MemoryLimit=4GiB、CPUQuota=200%、Nice=15；两版数据库缓存各 512 MiB、latest 状态缓存 128 MiB。没有 P2P、导入器或生产启动逻辑。

完整 HTTP 经过 JSON-RPC handler、TronBackend 和 TVM，使用 loopback HTTP，消除外部代理网络差异。固定合约 `0xa4997124a328a4615eab437cede31da47a31b375`，调用数据 `0x9fa6a6e3`；7 个高度覆盖 3,144,020、3,144,021、5M、9M、head−256、head−1 和 latest，预期整数依次为 6、7、63、207、225、225、225。结论只覆盖该固定读存储调用，不能代表所有 TVM 合约。160 次已记录请求全部与独立预期返回值一致，其中 112 次进入性能分组。热缓存每点每版 4 次，新进程及独立 OS 冷缓存各 2 次；不根据少量样本推断 p95。

首轮及追加总计 192 次 eth_call 全部返回正确，其中 144 次计入性能分组。9M 冷缓存仍没有证明稳定收益；中位数轻微上升且范围重叠，不能据此断言稳定退化，也不能宣称完整请求秒级问题已解决。其他早期高度也有约 1 秒样本。当前系统键拆分只解决其中一条支路。

冷缓存定义为经字节 SHA256 核对的独立 inode；驱逐这些测试文件的页缓存，mincore 驻留率低于 1% 后启动诊断 HTTP 进程。没有执行全局 drop_caches。因部分高度的冷样本波动较大，追加 4 个高度、每版 4 次交错采样，结果在最终回执中单列。

这个固定副本有 4,609 个冷源、34 个实际系统键；新路由 158,489 B，缓存计费 609,413 B，4,609/4,609 源已严格核验。它不能单独代表当前 27,893 段目录的规模。

## 当前目录规模

固定目录清单 SHA256 为 `47771ab6fa19bd3ce717afe1bfd6bf67143743b6cae8a620604aa17d1ece2bde`，有 149,059 个活动文件引用，其中 state-domain-change 冷源 27,893 个，accessor 实际文件合计 217,438,436,199 B。源文件通过不可变对象硬链接固定，不复制运行中的 Pebble。第一次采集碰到退休文件，已重采并取得完整一致清单。

全源构建和严格成员校验通过，27,893/27,893 源覆盖完整。新路由实际发现 60 个键，文件 952,774 B、解码缓存计费 3,645,462 B。构建 1,877.417 秒，独立严格检查 1,853.289 秒，诊断进程整体峰值 RSS 441,872 KiB。预算计费不代表峰值 RSS；本次全量初始化及独立检查约 62.5 分钟，不能视为没有构建成本。60 个键为系统账户 1 个、DynamicProperty 45 个、ForkVote 14 个。比旧表多出的键是 generation=0 的 `allow_tvm_london`，旧表 59 个系统键均保留；59 不是格式或发现上限。

这里的批查询是冷 Manager 的 60 个实际系统键及一个已知不存在键查询，范围为 9M 后到固定冷目录末端，不能冒充完整 HTTP eth_call。第一条样本是新进程且 OS 缓存不受控；每个进程的后 4 条作为暖缓存样本。原 B,C 两次进程带 open/openat 跟踪，后 C,B 两次为无跟踪原生复测；两类延迟必须分开，不能把它们合并为同一种 ABBA 延迟样本。无跟踪每版 4 次热样本的中位数 1.451038 秒 → 0.228314 秒，约 6.36 倍；结果完全一致。跟踪数据只用于读文件路径和次数的诊断。

旧大路由仍供合约查询使用，新索引是额外约 1 MB 磁盘占用。不能把系统查询少读的大表字节数报告成全库回收量。

旧混合路由的完整字节在服务器上重新计算 SHA256 并精确拆分，本地取回源身份前缀和完整 census；没有声称已下载其全部 66.95 MB payload。结构如下：

| 项目 | 旧混合路由 | 新系统键路由 |
|---|---:|---:|
| 覆盖活动源 | 25,600 / 27,893 | 27,893 / 27,893 |
| 键数 | 951,169 | 60 |
| 文件字节 | 66,948,766 | 952,774 |
| 保守解码缓存计费 | 307,198,576 B | 3,645,462 B |
| 是否满足 64 MiB 缓存准入 | 否 | 是 |

旧表中 951,110 个 ContractStoragePrefix 编码占 66,073,468 B，约占整个文件 98.69%。其解码计费超过准入预算，后续请求仍需重复读取、认证、解码；另有 2,293 个活动源没有旧覆盖证明，需要原始读取器回退。旧物理文件距 64 MiB 文件上限仅 160,098 B；进一步增长受限是合理风险，但本轮没有以缺失的生产构建日志声称已证明它为何停在 25,600 个源。

同一进程启动及 5 次批查询的 open/openat 跟踪窗口中，旧混合路由成功打开次数从 5 降到 0，history `.kv` 从 11,620 降到 160。轻量文件的 6 次打开包含诊断程序一次读取键名单，不能全部归为 5 次业务查询。次数仅描述这个完整跟踪窗口，不能直接当成任意单条 eth_call 的稳态计数。

无跟踪批查询的单进程峰值 RSS 基线 778,544 KiB、候选 298,260 KiB，包含 Manager 初始化和 5 次批查询，不是单条请求的内存增量，也不是硬性上界。首条新进程、OS 缓存不受控的查询为 1.931153 秒 → 0.229606 秒；后 4 条热样本范围为 1.391926–1.468148 秒 → 0.213187–0.260599 秒。


## 正确性

固定副本全量重算 144,903,091 条状态源行，MuHash 为 `8fbf149684146a59b1650b318a768f0edbae0c8c1c3ceb2c5c610129c10f76a5`，与原 HEAD 一致；本次实测约 891 秒。三个各 20 块的历史窗口实际恢复及完整行摘要比对通过。这是固定副本的全量状态复算及历史恢复，不是当前线上 43M 状态的全量复算。

本地通过完整 snapshots 包、core/state/rawdb 历史及 MuHash 测试、race、vet 和构建。Astra 对路由边界、维护游标及性能结论进行了只读审查；本任务独立复核源码和原始数据，没有把顾问审查当作统计来源。新增测试覆盖空成员源、未来新键、超过 64 源的一遍构建、源替换/新尾/游标环绕、旧 V1/V2 混合路由、损坏与语义遗漏、取消、退休保护，以及带新路由的严格和签名快照目录恢复、恢复后 MuHash 复算。

## 已定位的剩余开销

在 11.8M 固定副本的候选暖缓存 CPU 采样中，`iterateHistoryOwnerSpans` 累计 44.80%，`latestSegmentRef` 累计 12.78%。前者在处理所选 owner 的行前仍需认证、materialize 整个源 pack，并对压缩 payload 整体解压；owner spans 主要省掉无关行的 RLP 解释。后者包含 currentManifest() 和线性遍历 manifest，不能把其累计时间全部归于扫描循环。这里是累计 CPU 样本占比，不是 HTTP 墙钟占比，类别可能嵌套，不能相加。

单条带跟踪的 9M RPC 窗口内，进程 rchar 增量从 23,280,327 B 降至 22,082,106 B；rchar 表示读取调用返回的逻辑字节，不是物理磁盘流量；跟踪耗时不纳入延迟分组。一次进程启动及一次请求的完整 trace 窗口中，旧大路由整读由 3 次降到 2 次，另新增两次轻量路由读取，次数不能直接当作稳态每 RPC 次数。整进程 trace 中 `.gtv2/.gtxi` 的大部分读取包含启动阶段，不能全部归到请求。当前大目录的旧混合路由仍可能为合约查询带来整表读取/解码；后续应优先评估合约路由分页、热尾的真正按 owner/页独立解压，以及 latest 目录索引。

本轮验证范围是：11.8M 固定全状态 MuHash、60 块历史实际恢复、单个固定合约的完整 HTTP，以及 27,893 段固定冷目录的系统键批查询。本地还覆盖带新路由的严格及签名快照恢复。这些结果不等于对当前线上全部状态重新计算 MuHash、当前大目录的完整 HTTP 验收，或所有合约/所有历史高度的性能保证。

下一步建议按瓶颈拆解：

1. 对 9M 固定 HTTP，先将热 history 旧值 payload 做真正的 owner／页独立压缩、认证和定位，限制单次查询的解压字节；保留块行顺序与完整恢复遍历，使用当前源身份约束辅助信息。现有 owner spans 尚不能消除整 pack materialize 和解压，这是候选暖缓存 CPU 中最大的已观测路径。
2. 对当前大目录，将 ContractStorage／ContractMetadata 路由分页，按 owner/generation 找到少量认证页，避免整读、整解码剩余 66.95 MB 混合表，也避免覆盖更新被表大小上限阻挡。系统键独立路由继续保留。
3. 将 latest 段选择按 manifest 代次建立目录索引，减少反复读取 manifest 和线性查找。先测量其独立 CPU 与墙钟贡献，不能把累计 12.78% 直接当作可回收墙钟时间。

这三项尚未在本轮实现或上线；本轮交付的是独立系统键路由及其离线验证。
