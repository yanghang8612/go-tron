# 冷库历史 eth_call 路由与读取优化验收（2026-10-21）

本次改动已在本地和固定主网副本完成实现与验证。线上保持原服务、原库与原二进制；没有推送、部署、重启、删库或从创世重同步。虽然允许不兼容格式，这次测得的主要收益来自减少错误候选冷段、缩小重复认证读取和取消无用预取，规范状态无需重建。

## 瓶颈证据与实现

此前请求级去重与批量读取之后，深历史调用仍有两个结构性开销：每次打开冷段要重新读取/认证夹在 128 KiB 压缩块中的小头部；缺失键又需要搜索数千个未来冷段。增加缓存不能消除后者。

1. **小头部分帧与复用已检查的文件描述符**（`e4805af5`）。把前 128 个逻辑字节独立成帧，后续压缩体的边界和字节保持不变；虚拟偏移、逻辑记录、校验语义保持一致。页表临时缓冲区按实际大小分配。新打开仍认证当前文件字节，未改为 stat/mtime 信任缓存。
2. **系统键精确路由**（`0b57081f`）。系统动态属性、软件分叉投票、合约元数据等按完整编码键定位候选冷段。负向证明绑定完整的不可变 history/accessor 配对身份，新增、替换、未覆盖段仍执行原读取。索引只由经过认证的字典生成，严格快照验证会重新核对语义。
3. **账户/代际保守上界路由**（`31b3ff7b`、`2e403c3d`）。账户 envelope 与 generation 键存储覆盖源中最大的 ToTxNum。缺失或上界早于查询起点时才能跳过已覆盖配对；过大的保守上界只增加读取，不会把存在数据判断为不存在。两级 4 KiB 页目录用 SHA256 认证，查询先验证当前根元数据，再验证实际使用的目录页和数据页。最多保留一个有界解码根；跨请求不保留页和描述符。正向命中仍检查完整 owner。
4. **派生索引回收**（`c7ef42cf`）。后台每次检查最多 256 个退休引用、最多回收 16 个文件。只允许构造器生成的完整 SHA256 辅助索引路径，并检查 active/published 引用、读租约、发布互斥、迁移 journal 和文件/父目录身份。任何不确定状态都延后。签名 catalog 发布也持读租约，避免与回收竞争。
5. **默认空 caller 按需读取**（`0b370448`）。未指定 from 的 eth_call 无须提前预取空地址状态。保留执行期间真实需求的原读取路径，非空 caller 的预取保持原行为；没有把未知状态写成不存在。

系统路由之后的独立诊断发现：合约 envelope 没有未来变化，账户批量查询却访问 **4,223 个冷段**。通用账户路由使该合约的无用访问降至零。余下的 47 次冷段访问全来自默认空 caller、最终仍未命中，取消其可选预取针对的是这项实测开销。

## 固定输入与比较边界

固定副本 `/data/gtron/eth-call-fixed-20261020-01/capture-1`：

- HEAD **11,818,192**，head TxNum **601,386,177**。
- 区块哈希 `0000000000b454d09a46886a40d09d8cbec73812d013f57de1fc803784acfdf6`。
- MuHash `8fbf149684146a59b1650b318a768f0edbae0c8c1c3ceb2c5c610129c10f76a5`。
- 4,609 个 history 冷段，规范历史记录 3,565,941,110 行。各阶段原始固定副本与规范 history 数据保留。

真实 loopback HTTP 请求经过 JSON-RPC handler → TronBackend → TVM → JSON 序列化。读服务使用 GOMAXPROCS=2、GOMEMLIMIT=3 GiB，同一组 Pebble 缓存预算；没有导入器、P2P、冷化或清理负载。HTTP 测试宿主 SHA256 为 `10e6015af7666bf83b5c405543681c368b7537f428b8278a3344f0312aacd3bf`，各版一致。

合约 `0xa4997124a328a4615eab437cede31da47a31b375`，data `0x9fa6a6e3`，省略 from、value=0。高度为 3,144,020、3,144,021、5,000,000、9,000,000、HEAD−256、HEAD−1、latest，期望值依次为 6、7、63、207、225、225、225。参考值由独立 before-image 回放 oracle 生成：完整冷逻辑键遍历和热行折叠，而非被测 first-seek/请求缓存/TVM 快速路径；它仍共享文件与行解码器，不是另一套完全独立的存储实现。

每轮 **154 个完整 HTTP 请求**，包括 112 个计时样本；发现读取集的 14 次、暖身的 28 次不进入结果。每个高度每个版本暖缓存 n=4，按 AB/BA 交换顺序；新进程、OS 缓存未控制 n=2；独立副本的 OS 冷缓存 n=2。冷缓存只对 strace 观察到的读集、且已证明独立于源库的 inode 使用 fadvise，并用 mincore 证明驻留比例 <1%；不用全机 drop_caches。结论不覆盖未观察的运行时路径、设备硬件缓存、生产并发吞吐或 p95。

## 构建成本与空间

- 系统路由：4,609 对源、34 个键、158,489 B，73 个有界批次，358.771 s，含严格字典复核。
- 账户路由：4,609 对源、3,419,768 个键、100,798,871 B，73 批次、473.119 s，含严格字典复核。活跃两类辅助索引合计 **100,957,360 B**（文件长度，约 96.28 MiB）。这些是派生索引，不进入 MuHash，也不改变冷构建/热清理前沿。
- 小头部分帧：全部 history `.seg` 文件长度从 48,379,073,819 B 变为 48,379,318,571 B，增量仅 **244,752 B**；不是整个 state-snapshots 目录的占用。
- 索引构建初期会留下旧代，因此完成了有界物理回收。独立实验副本中的 **144 个旧辅助文件**均为单链接独占 inode，实测释放分配块 **3,914,711,040 B**，对应文件长度 **3,914,238,960 B**。9 个有界批次、0.223 s，manifest 字节不变、23,691 个规范路径的 inode/大小不变。原始实验输入的副本仍保留，所以不是服务器总盘净减少同样数值。

尝试过把规范冷段大规模合并，已在 34 个提交批次后主动停止：累计处理 1,162,677,763 行、耗时约 40.54 分钟，尚未得到完整合并副本的查询验收，不能声称合并有某个加速比例。另有 3,383/4,440 个叶子单段就超过 40 万记录的忙期预算；盲目提高线上合并预算可能挤占同步。保留现有小批量规范合并，把本次主要收益放在辅助路由上。

## 正确性与恢复

- 本地及服务器 Linux/Sapling 相关包测试、race、vet、原生构建通过。完整 snapshots 包包含损坏、截断、覆盖缺失、源替换、owner/generation 别名、页认证、取消与资源上限测试；回收测试覆盖读租约、已发布 catalog、journal、不可信路径、缺失文件和游标进展。
- prefix 实验对所有 4,609 文件做物理原件校验及逻辑 round-trip，后续压缩体字节/边界和虚拟偏移保持一致；原生 writer 在五个真实文件上的输出与实验转换器整文件 SHA256 相同。
- `c7ef42cf` 在清理后固定副本上全量重算 MuHash，通过。Account/Generation/KV 行数分别为 **3,484,117 / 481 / 141,418,493**，根为上述 `8fbf…76a5`。最终 `0b370448` 只改变只读预取选择，不改状态提交或 MuHash 数据；最终完整 HTTP 宿主仍核对同一 head/hash/root。
- 三个真实主网冷历史窗口（3,144,020、5,000,000、9,000,000 起各 20 块）实际调用恢复路径，合计 **22,496 行变化、60 条区块交易范围**；原始、候选、恢复后的全行摘要一致。恢复测试适配器从独立验证的 StateTxRange 补全 rawdb 返回值本来省略的 BlockHash。另有快照 CLI/单元恢复回归；未声称对整个 11.8M 历史做了一次完整快照导出/导入。

## 剩余瓶颈与使用方式

2e 版本独立 20 秒 CPU profile（排除主比较）显示，约 63.7% 累计 CPU 落在未索引热尾部 first-change 读取，约 62.95% 在 owner tail 迭代。Snappy、Zstd、RLP 行扫描占主要 flat CPU。这里反映的是**重复解码大量热尾部行**，不能据此把所有慢查询归咎于压缩算法本身。

最终 9M 的两次 OS 冷请求，handler CPU 中位数 **391.529 ms**，分配 **26,617,160 B**，实际 read_bytes **72,454,144 B**，syscr **5,651**。CPU 没有解释全部 1.54 s 延迟。进一步用同一最终二进制、已证明私有的冷缓存 inode，单独追踪一次 9M 完整 HTTP；返回值仍为 207。这次 strace 运行约 2.227 s，有追踪开销，**排除性能比较**。按请求时间窗口归属的 5,647 次输入文件 read/pread64：

| 文件族 | 调用数 | 返回字节 | 累计 syscall elapsed（s） |
|---|---:|---:|---:|
| 热 history Pebble `.sst` | 1,666 | 14,660,137 | 0.577829 |
| 冷 accessor `.kv` | 2,874 | 4,424,857 | 0.434696 |
| 冷历史正文 `.seg` | 1,062 | 2,801,506 | 0.370640 |
| 状态 chaindata `.sst` | 35 | 1,052,915 | 0.016191 |
| 新辅助路由 `.route` | 8 | 497,673 | 0.006098 |
| 其他输入 `.gtv2` | 2 | 572,504 | 0.002419 |

syscall 时间可能跨线程重叠，不能把这一列相加当作不重叠的请求耗时。原始追踪、100 条未归属窗口行（主要信号与 socket EAGAIN）均保留。由此可把下一步落实为：**热 history 的首次变化结果在请求内复用**，减少重复尾部扫描；**冷 accessor/正文的相邻读取合并及经过认证的请求内页复用**，减少小块随机 I/O。新的 `.route` 根/页不是当前大头。更广的按键全局索引需要另测磁盘和构建成本，不能假定免费。

新全局辅助索引也有更新成本：每次最多覆盖 64 个新源，账户构建还限制 800 万字典键、使用 32 MiB ETL 排序并与已有有序表流式合并。未覆盖源自动走原读取路径，索引追赶期间允许性能逐步改善。后续若扩大工作负载，应先覆盖其他合约、多 slot、非空 caller、revert/creation 和并发，再针对热尾部按 owner/domain 的首次变化缓存或页式索引继续优化；本次没有拿单个计数器合约的结果替代这类验证。

现有库可以重建辅助索引；旧头部布局仍可读，新产出的冷段才使用小头部帧。无需为构建这些辅助索引强制从创世重同步。性能表使用的是已经转换小头部布局的离线副本；仅更新读取代码并建立索引、保留既有旧布局冷段，不能直接承诺同样延迟。获得完全相同布局需要有界离线转换或重新同步，均未对生产执行。带新 manifest 家族的目录需要相应新版本读取，不能把它直接交给不认识这些家族的旧二进制。保持生产现状，待用户另行授权发布。
