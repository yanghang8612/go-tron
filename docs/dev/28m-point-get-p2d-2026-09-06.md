静态分析确认：SeekPrefixGE 虽保留 full-key Bloom，但 merging iterator 会定位所有重叠层。Pebble v1.1.5 Snapshot.Get 的 getIter 按新旧层惰性查找，可在找到快照可见值或删除时停止旧层读取。新路径使用原 snapshot sequence、prefix 范围、overlay cut、cache epoch、singleflight 和全局 32 个 durable 名额；合并、删除与错误由 Pebble 原实现处理。返回值只在回调期间有效，异常和 panic 同样释放 closer。

启动开关 `GTRON_PEBBLE_BOUNDED_POINT_READ=get` 只改变非空 prefix 的 cursor；空值或 `iterator` 保持原实现。无界状态批量预读继续使用排序游标。未知值在打开 DB 前报错。默认没有改变。磁盘格式、root、branch rows、交易验证和历史语义均未修改。

新增 `blockbuffer/commitment_parent/pebble/get/{cursors,calls,hits,errors,nanos}`，nanos 排除回调时间。Pebble Get 没有完整内部块统计，所以不能把新模式下旧 iterator 指标减少解释成 I/O 已消失。线上必须结合全局 VFS ReadAt、profile、工作量和压实积压判断。

首个 Get 窗口 tx/s 比前组高 24.6%，但交易密度也高 30%，blocks/s 低 4.1%；不能只挑 tx/s 宣称严格整链提速。更强的证据是同开关反向复现的提交成本：iterator 两组 293/336 µs/update，Get 为 57.6 µs/update。随机 VFS ReadAt 也减少，但顺序读与历史压实活动不同，不能把全盘 I/O 都归因于该开关。Get 首组压实债务 100.58 → 92.09 GiB，iterator 两组分别 94.50 → 96.41、95.49 → 92.92 GiB。

最后一对复测的 energy/tx 仅相差约 1.2%，Get 的交易密度高 10.6%、VM 交易占比也更高；blocks/s 约两倍，commit/update 下降 83.1%。这个重复切换结果支持在当前主网数据形状保留 Get，但仍不把不同区间的吞吐比当作精确因果倍数。最终 Get 窗口压实债务 90.47 → 91.71 GiB，有波动，长期追平能力尚待后续观测。

52 个剔除预热后的点全部 active，无相关错误增量；Get 两组共 4,633,024 次点读错误为 0。所有窗口均只有一个 PID。首个 Get 组 RSS 更高且压实更活跃；最终匹配窗口 RSS 峰值 18.149 GiB、前一 iterator 组 17.947 GiB，尚不能把全程峰值差异全部归因于 Get 分配。

四组 P2d1 CPU 样本的 Build ID 均为 `3166c83a91f31fc3e6d8c52c33bda4b4859e98ef`。三个 Get 样本分别受到历史压实 24.17/13.86/24.22 CPU-s 的影响，回切 iterator 为 21.41 CPU-s。Get 后续仍需关注历史源文件全量 checksum 及 Pebble 压实，但不能将某次周期性任务的占比推广到全天。采样原始文件保存在本地 `cpu-*.pb.gz`、对应 `top.txt` 与 node JSON。
