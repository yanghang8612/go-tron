## 修复方向与限制

先比较相同总输入的有界并发构建，分别统计速度和输出量；增加小段会影响压缩率、
清单数量及后续合并，不能仅看构建提速。优先验证单个冷三件套内部的按块并行认证、
有序消费，保留两遍扫描和原输出格式，以解码字节与任务数共同约束在途内存。

若仍不足，需要改变历史的物理表示，使大旧值不再重复展开、重新切块与哈希。
自包含的冷引用容器或有界 checkpoint 加增量必须有完整 reader、索引、合并、
裁剪证明、崩溃恢复和新旧双读。不能永久引用随后会被热 GC 删除的 chunk。

只拆分当前 delegation 列表的存储键，无法自动消除已经保存的百万块旧积压。
直接提前切换 proposal 69 的关系键还会改变历史链上行为；物理改造必须保留相同逻辑值、
顺序、存在性、交易版本与 commitment。旧 pack 至少仍须完整认证一次。

本地原始数字与命令记录位于 `build/benchmarks/20260915-root-cause/`；原生采样和
完整报告位于 `/data/gtron/releases/20260915-history-range/result/`。设计约束见
[固定范围与并发方案](../superpowers/specs/2026-09-15-cold-throughput-root-cause.md)。

### 首次旧文件认证暴露的批量估计问题

上线初期部分批次从约 180 块缩到 23–28 块，但构建本身只需约 1.4–1.9 秒，
`PrunePass` 却需要约 7–8 秒。日志确认 88 次认证对应 **88 个不同路径**，全部为
`persistent / hot prune coverage`，总 checksum 字节约 17.818 GB；没有同路径重复认证。
现有证明缓存没有按清单 generation 清空。它是共享历史 GC 遍历旧桶时触发的首次校验，
并非新 reader 重复校验同一冷文件。

源码仍把这段与当前构建范围独立的 GC 扫描、覆盖认证和 guard 工作计入每批历史块的
密度反馈，导致旧回收越忙、新构建批次反而越小。新增窄修复已精确记录整个共享 GC
阶段，只从范围密度估计中剔除；完整维护耗时、恢复等待和所有删除证明仍全额保留。
不能把元数据时间重复剔除，也不能把 GC 成本从总资源预算里隐藏。

该修复本地 Go 1.25.5 的 snapshots/pruning 全包测试与 vet 通过；定向 normal、race 两轮
通过。覆盖真实 Worker 的 scan/proof/guard 完整计时、真实 lifecycle 转发、相同历史工作加
独立 GC 不缩小批量、无效/重叠/溢出计时保守回退，以及完整维护和恢复期限不被少计。
此处是本地验收记录；上面首轮 12 分钟收益不能归给该计费修复。其后原生与上线验收见下。
