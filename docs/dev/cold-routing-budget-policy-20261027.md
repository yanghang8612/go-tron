# 大路由预算失败后的自适应维护验收（2026-10-27）

本次只修复 broad system history routing 维护预算失败后的重复构建。此前工作树中的 small-system 轻量路由同时存在于基线和候选版，不能把轻量路由已取得的查询收益再次计入本次改动。线上服务、二进制、参数和数据库均未切换。

## 根因和实现

固定冷目录包含 27,893 对 state-domain-change 源，原 broad route 覆盖 25,600 对、951,169 个键，占 66,948,766 B；距 64 MiB 上限仅 160,098 B。旧维护路径每次尝试追加最多 64 个源，整体预算失败后没有产出，下次维护又从头扫描并构建。

候选版每次构建只认证一次旧路由，并在本次构建内复用已认证的新源键。64 源装配失败后直接尝试 1 源，最多进行两次装配；成功后记住小批量。连 1 源也放不下时，采用 1 分钟起、最长 30 分钟的指数退避，并轮转失败起点。只因格式/源大小不支持而无进展时使用 15 秒退避。源身份替换、退休或相关输入变化会取消退避；失败前缀之后的尾部追加不会不断触发重建。

调度状态由 Runner 的 passMu 保护，只保留身份和游标等提示，不作为历史查询的存在性或缺失证明。查询、严格快照导入继续使用物理认证。未改变 GTSYSR01 V1/V2、canonical 段、MuHash 逻辑输入和历史值编码。

## 固定副本和资源条件

同一 11,818,192 高度副本，TxNum=601,386,177，block hash=0000000000b454d09a46886a40d09d8cbec73812d013f57de1fc803784acfdf6。完整 HTTP 查询使用相同 manifest、相同轻量路由和相同规范数据；维护压力使用同一大冷目录。HTTP 的状态副本有 4,609 个冷源，维护压力目录有 27,893 对冷源；压力目录用来运行独立维护任务，不冒充 11.8M 状态副本。两种进程共享本次 2 CPU 配额，模拟资源竞争，结果不能直接代表线上 16 核条件。

原生 Go 1.25.5，离线 systemd unit 限制 CPUQuota=200%、MemoryLimit=6G、Nice=15。HTTP 主机 GOMAXPROCS=2、GOMEMLIMIT=3GiB，history/hot 缓存各 512 MiB；维护进程 GOMEMLIMIT=2GiB。线上同步继续运行，主机负载并非完全静止，记录了各阶段环境并采用交错顺序。

冷缓存只对事先独立复制并重新核验大小、SHA256 和 inode 隔离的数据文件调用 fadvise，不做全局 drop_caches。2,255 个文件共 68,457,590,932 B，其中 2,245 个复用已证明独立的不可变 inode，10 个 WAL/manifest 等文件重新独立复制。

成功扩展仍需重写完整路由和 manifest。最终活动路由只净增加 158,436 B，但50 次新路由文件累计 3,350,488,523 B，计时循环末进程累计 write_bytes 基线 58,933,248 B、候选 5,456,146,432 B。后两项还包含私有 manifest、冷构建和诊断输出，不能称为纯路由写入量。多次成功会有明显写放大；离线保留所有中间路由的占用也不能当作线上稳态净增长。后续应评估分片/增量路由与合并发布，保持当前认证和退休协议。

## 生产 auto 冷构建入口

原始副本的恢复接口生成 legacy 单行 history，生产借用式 builder 要求完整 block pack；仅将可丢弃夹具重新按执行路径写成完整 block pack，保持所有行内容/顺序和 canonical TxRange。4 次显式 auto 构建均逐行校验，输出 2,431,014 B（seg 1,697,906 B、kv 672,584 B、idx 60,524 B），两版本文件校验和一致。

首轮顺序测量总耗时基线 1.089023135 s、候选 1.209245257 s，CPU 分别为 1.170635 s 和 1.278948 s。小窗口约 10% 的差异需要交错重复核对，不能用代码未改便宣称没有回退。另以相同已认证窗口做 B/C/C/B 交错、每进程 1 次不计时预热和 8 次计时构建，每版 16 次：中位数基线 305.86 ms、候选 293.89 ms；范围为 275.88–738.54 / 268.16–563.05 ms。CPU 合计 5.447960 / 5.181253 s，计时合计 5.482866 / 4.966938 s。未复现首轮约 10% 变慢，测量方向随轮次改变且范围重叠；本次没有修改冷构建算法，不把这几%的波动宣称为稳定构建收益。源窗口定位准备约 7 分钟，单列于构建计时之外；后续使用同一已认证窗口避免反复做这项准备。

## 正确性及验收限制

每版 8 个重建段均核对全部行内容和顺序、256 个区块 TxRange；首个重建段恢复到空热库后逐行读回 121,637 行，并核对 16 个 posting 查询。V5/V6 的 Seq 含段内记录序号，重新分段会改变低 32 位；因此内容比较只规范化派生 Seq，并独立核对其精确公式、顺序和无碰撞。原始副本窗口恢复仍核对包含 Seq 的整行摘要。

旧路由成员关系双向相等，新加入的 50 个源逐一认证源字典并核对成员数。这是增量证明，未重新全扫此前已认证的 217 GB 旧源字典。

本地 snapshots 全包、core/state/JSON-RPC、相关 race、vet 和 gtron 构建已通过。原生全量 MuHash 重算耗时 903.09 s，144,903,091 个源行（3,484,117 / 481 / 141,418,493）及三个源摘要均与先前固定副本全量结果一致；根为 `8fbf149684146a59b1650b318a768f0edbae0c8c1c3ceb2c5c610129c10f76a5`。三个 20 区块历史窗口共恢复 22,496 行，原始、候选和恢复后包含 Seq 的整行摘要相等，60 个 TxRange 相等。

原生初轮包含 10 个 policy 用例，但未包含后来追加的目录隔离用例及最新 small-system 签名恢复用例。因此在所有性能测量结束后，单独原生编译最新两个测试文件并核验测试名列表，26 个 policy/small-system 用例全部通过，包括严格 manifest、签名 catalog 恢复及恢复后 MuHash 核对。更新仅为测试源码，性能测量使用的产品 10 文件摘要保持不变。

诊断程序曾因重分段 Seq 直接比较、legacy 单行热库夹具、Python http.py 名称遮蔽及 metadata inode 断言而失败；均保留原始日志并修正测试夹具/验收程序。产品代码未因此变更。基线 64 次有效计时完成后，旧验证器重复构造 lookup view，已只重跑验证阶段；基线 cpu.pprof 属于重跑验证阶段，不能与候选完整过程 profile 比较。
