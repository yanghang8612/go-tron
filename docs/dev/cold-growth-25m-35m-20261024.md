# 25M–35M 冷库增长：按真实高度分组的只读核验

用户观察有依据：在同一份已发布冷清单中，完整落入 20M–25M、25M–30M、30M–35M 的文件分别占 **87.477 / 111.397 / 127.731 GB**。后两个区间比前一区间分别多约 27.35% / 14.66%。GB 均为十进制文件长度，不是文件系统 allocated，也不是过去在这些高度实测的整库占用。

## 样本与口径

- 只读采集 2026-10-24 的线上 manifest，SHA256 `840c8e1d4698f7c42f542a9b0eb2f0f03d250f21fd15ea3d049c2f30f34ee87b`，冷清理前沿 **35,819,894**，状态 TxNum **2,658,305,819**；读取冷段首尾交易范围表恢复真实区块范围，不把状态历史文件名的 TxNum 当作高度。
- 合并旧冻结清单与当前清单，共扫描 22,121 个唯一历史段路径，22,119 个可读。旧冻结 19,949 段全部可读；当前两个末尾段在采样读取时已不在原路径，位置均在 35M 之后，不影响本文三个区间。这里验证读取到的压缩块及头/范围元数据，不声称重新哈希了全部 `.seg` 数据体。
- 所有可读历史段均从完整块的 BeginTxNum 开始、在完整块的 EndTxNum 结束。三个目标区间内部块范围和 TxNum 连续、无重叠和缺口；跨越 5M 分界的整个文件单独列出，不按字节比例猜分。因而下表是完整落在区间内的文件和块，不是恰好每区间五百万块。
- 状态 TxNum 每块包含一个块末维护位置；真实交易数 = TxNum 跨度 − 实际覆盖块数。事件日志的 manifest 复用 FromTxNum/ToTxNum 字段存放**区块**边界，这是该 dataset 的构建契约，与状态历史字段口径不同。两者分别解释后归组。
- 这是同一时刻不可变文件的高度分布，未包含历史上 LSM 放大、临时文件、已退役文件和文件系统回收滞后；不能替代“节点在 25M 时的磁盘快照”。事件日志与状态历史的分段边界也不同，合计只表示完整落入同一高度区间的文件。

交易量显著增加，单位交易历史文件占用同时下降。这支持“交易密度是区间文件增加的重要原因”，不支持直接把增加归因于压缩失效。另一方面，单位变化记录 `.seg` 占用约 16.30 → 17.43 → 18.01 B，`.kv` 约 11.18 → 13.85 → 16.58 B，说明记录类型和键分布也在变化，不能仅用记录总数解释。

事件日志在 30M–35M 的合计比 25M–30M 略小；这个阶段的主要增量来自状态历史，特别是 `.kv`。这是一份分布归因，不是对不同高度、不同工作负载的优化 A/B。

## 键分布的变化

数据类型拆分依据已经全量核验的 19,949 个 `.kv` 字段统计，**其最晚高度仅为 33,248,191**；以下第三行是 30M–33.248M，不能冒充完整 30M–35M。键数量按段内实例累加，不是跨段去重后的地址/槽位数量。

后一窗口 AccountAssetV2 为 305,873,618 个段内键实例，其中 256,332,773 个是段内单次变化；ContractStorage 为 113,000,936 个键实例，占 14.818%，账户 flat 为 243,644,669 个，占 31.949%。因此，后续字典优化应同时覆盖账户和 AccountAssetV2，而不能只围绕 ContractStorage。这里没有追溯具体合约或业务原因。

上述 domain 计数与各域原 posting/逻辑键字节可精确拆分；但混合键页经前缀编码及 Zstd 压缩，不能把某域逻辑字节直接当作它的物理压缩占用，也不能把 `.kv` 的比例外推到 `.seg` before-image。

## 与正在验证的优化的关系

本线程的单次变化内联 V8、共享 offset 页 V9 都是独立离线候选，没有部署到这个生产目录。不能把线上 25M–35M 的增长描述为它们已经上线后的效果。

V8 针对单次变化的独立 posting 开销，V9 针对多次变化的重复 offset；它们不会删除历史变化。键实例增长的证据提示，共享字典/owner 分组及有界段合并值得在后续单独测量，但必须计入映射、目录、随机查询、生命周期和快照闭包的成本。当前继续完成 V9 的同一冻结 cohort 空间核验，以及 11.8M 完整副本 HTTP、MuHash 和恢复验收；后者不代表 25M–35M 的 HTTP 已验收。
