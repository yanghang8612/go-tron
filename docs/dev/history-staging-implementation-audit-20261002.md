# History staging implementation audit — 2026-10-02

Audit baseline: `2e9cc1007c0e61ae7b293434c27d9e9af2f823e0`. Astra performed an independent read-only implementation audit while Sol made the reviewed fixes. This is not a claim of exhaustive review or a production throughput result. The auditor traced planning, cold proof/authentication, copy/adopt/delete, cold bindings and read leases, pre-plan repinning and activation recovery, and reader startup. The first four fixes were committed and deployed as `59442e305bc7bd4f62544cbf1a6a937bee03ab0b`. At the time of this review, the fifth root release-helper ownership fix had not been installed; its subsequent commit, installed-helper SHA, and production outcome are recorded by the release operator in `build/benchmarks/20261001-history-staging-online/status.json`.

## Confirmed issues and fixes

1. `collectSpanRecords` wrapped the concrete history reader in `contextReaderAt`, preserving cancellation but hiding its cached header and transaction-range cursor. V5/V6 records then reread the header and binary-searched the range table for every row. The proof now uses the already authenticated header and one forward range cursor per span. Record framing, V6 dictionary resolution, block hash and transaction range checks, sequence/ordinal recovery, previous-value semantic digest, file fingerprints, and cancellation remain in force.
2. Non-V7 full-trio index coverage had the same wrapper regression. It now receives the validated header and advances a range cursor while preserving the visitor, index ordering, exact record/byte coverage, and V1/V2 embedded-context behavior. V7's separate sequential coverage path is unchanged.
3. The persisted-reader startup guard required `StateHistoryIndex` at the head even though the offline migration accepts a canonical lagging index and the constructor verifies and preserves it. The guard now requires a present, hash-bound, canonical index at or below the head. It still requires `Finish` at the head; it does not silently build or advance the index. At the observed pre-cutover boundary, head 33,274,674 and index 33,270,266 differed by 4,408 blocks, so the old guard would have refused this valid state.
4. A retry in `VERIFIED_PENDING_ACTIVATION` reran the pre-plan legacy manifest SHA inspection. An already started reader can legitimately publish a new manifest before the migration journal reaches `DONE`, making that old SHA fail. Only `MIGRATION_IN_PROGRESS` performs that inspection. Pending activation retains the fixed candidate and durable activation intent checks; the new reader verifies the persisted route barrier before passing startup health. Failed activation leaves the latch in place. The inactive-service completion path still runs offline `verify-complete`, but the fifth fix deliberately refuses ownership handoff for that path.
5. The root offline CLI can leave source and staging Pebble files and the staging directory owned by root, while the pinned service runs as `java-tron`. The separate release-helper patch performs a durable, bounded, exact-path ownership handoff only after verified activation intent and before starting the reader. It checks the parent orchestrator's four exact BSD locks, both Pebble POSIX `LOCK` files, a strict flat-file inventory, service UID/GID and stopped systemd units, then transfers only vetted source/target files and directories. It preserves modes and payloads, leaves root migration locks untouched, probes service access, and rechecks every inventory entry. A root-only journal makes partial handoff resumable; an already running exact pinned reader is accepted only with a matching `DONE` journal and process identity. The hotfix refuses jobs whose old service was inactive because that branch's later root CLI verification could create new root-owned files. At review time, production execution evidence for this fifth fix was still pending.

## Other reviewed paths

The planner bounds active and pending work by its worker count, writes ordered deterministic output, and joins workers after cancellation. Cold trio authentication uses immutable-file fingerprints, rejects replacement, and does not cache a failed singleflight result as success. Plan content digest, job identity, pristine checks, exact same-job temporary cleanup, and durable repin intent were reviewed. Source deletion remains behind target verification, receipt and route publication with sync, bounded delete, and an empty-source scan. Cold binding reverse references and old read leases guard physical retirement. Partial plans cannot publish an activation barrier, and missing staging data does not silently fall back to the source.

## Verification and limits

Real 1,024-range, 8,192-row V5, V6, and V7-reference fixtures produced the same semantic digest as the old wrapped decoder. The proof path used 29,710 history `ReadAt` calls versus 131,088 before; non-V7 full-auth index coverage used 17,420 versus 131,088. A mid-read cancellation test passed. One-iteration M1 Max benchmarks measured V5 proof at 5.60 ms versus 14.73 ms and reference proof at 7.66 ms versus 23.44 ms; these are local microbenchmarks, not an estimate of online migration time. Constructor tests cover valid lagging progress without mutation and rejection of missing, unhashed, wrong-hash, and ahead progress. Python tests cover successful pending retry and fail-closed activation failure.

`go test ./core/state/snapshots -count=1 -timeout=300s` passed (93.0 s), as did `go test ./cmd/gtron -count=1 -timeout=300s` (54.9 s), focused snapshots race tests (21.6 s), all 18 migration Python tests, and `git diff --check`. The race selection covered the cursor, full-auth index coverage, and compressed-opener audit tests. Existing dual-Pebble phase recovery tests close and reopen stores at copy, adoption, and partial-clear boundaries; they are not power-loss or `SIGKILL` tests. Startup checks TARGET receipt metadata and pinned cold dependencies, but does not rescan every TARGET physical row. The protocol review found no legal copy/adopt/GC/reset window that leaves a live receipt without payload. Arbitrary storage damage or manual deletion of a still-decodable changeset row may therefore escape startup checks; offline `verify-complete` scans the physical payload digest, while a missing chunk or malformed encoding fails on read. This review does not claim full-repository coverage or production crash safety.

Application remains serial. A newly encountered cold bucket can receive repeated full semantic proofs in apply and again during `verify-complete`; startup also performs full trio authentication. The migration watchdog, activation health timeout, production I/O impact, and final route verification still need to be observed in the guarded release workflow. The local `ReadAt` reduction alone does not establish that the live bottleneck is solved.
