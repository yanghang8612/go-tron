## 已证实的增长因素与尚未证实的部分

**每块新写历史明显变重。** 同进程两段窗口的 block-pack 计数差分显示：

| 历史变更包密度 | 昨日上线后窗口 | 今日窗口 |
| --- | ---: | ---: |
| 变更行/块 | 469.73 | 684.82 |
| key+已编码包字节/块 | 26445 B（25.83 KiB） | 62358 B（60.90 KiB） |
| 编码压缩前字节/块 | 51320 B | 93540 B |

key+包写入量每块约为昨日的2.36倍。它已包含应用层包编码/压缩，尚未计入 Pebble 的压缩及版本回收，属于累计写入流量，不是当前保留空间。热历史边界按 block 高度，保留约33万块并不意味着保留相同字节；更多变更、更大旧值和不同压缩率会使同样块数的窗口变大。这是直接测得的密度变化，但不能乘积压块数就宣称准确 SST 占比，也不能用当前六分钟解释过去整段时间的全部增长。

**当前状态和更新旧版本尚未分账。** 新账户、storage key、较大值、commitment 分支会增加状态存量；反复更新的旧物理版本则需 compaction/MVCC 处理。当前 HTTP 没有键空间物理估计或完整 snapshot/obsolete/WAL 分解，不能将新增59.69 GiB准确分配给这些类别。昨天记录的 commitment flush 写入占比也不能当今天 SST 存量占比。

**同步期部分维护有意延期，但不能过度归因。** 配置会推迟全量 latest 冷快照扫描、commitment baseline 轮换和部分 Code 清理。普通 latest 快照生成并不会按水位批量迁删 Accounts/KV，所以不能把它延期直接称为“账户本应迁冷却卡住”。分支轮换确有清理旧 generation 的路径，但是否存在大量可清旧分支仍需具体 keyspace/generation 证据。固定的 latest_build_block 是恢复的水位，不证明启动时生成过新快照。

**压缩在运行，尚无写停顿。** 07:25–07:31窗内compaction输入/输出约51.58/42.35 MiB/s，累计输出约14.89 GiB；引擎写入工作量约71.80 MiB/s。它们是重复重写的工作量，不是净增长。Estimated compaction debt为9.97→10.45 GiB，范围6.97–11.42 GiB；它表示预计待处理工作量，不是可删除垃圾大小。L0子层1–4、write stall增量0、物理SST读取错误增量0。设备busy中位数94.72%，await中位约0.812ms，设备繁忙但不能仅由busy证明某个资源硬饱和。

08:29–08:30补采的compaction debt为11.57→13.53 GiB，三点峰值14.04 GiB，较前一轮更高；L0仍1–4。最近一分钟及约一小时端点间，write stall和物理SST读取错误均无新增。压缩工作量值得继续观察，但不能把该debt直接作为可回收容量，或用一分钟波动预测写满时间。

此前新增复用 observer 保存的是有界内存记录，不写业务数据库；不能把它的136.5KiB诊断结构解释为几十GiB chaindata增长。仍不能仅凭当前指标排除层内旧版本保留或 snapshot 问题；`table/zombie`是memtable数量，`iter/count`也不是长寿命snapshot计数。

## 后续优化依据与当前限制

实际目录、SST/WAL和剩余容量已经补齐。本次采用三段只读探针分别读取目录/容量、文件stat/proc fd、日志尾部；`server_readonly_probe.py`保存合并参考实现，未把它标为原样执行。终端结果人工转录至`server-filesystem-observations.json`，明确标注来源；原始HTTP响应仍独立保存。

剩余的关键取证是**有界keyspace物理估计与snapshot/obsolete/zombie/WAL拆分**，用于区分热历史、当前账户/storage、commitment以及旧物理版本。这应先于调整清理策略。现有HTTP没有这些入口；最近1MiB日志没有hotHistoryBytes/build-started记录，不能把缺失当零。已看到历史发布与prune日志，且水位匹配。

优化方向是让历史保留与调度同时考虑字节压力和块数，并用上述观测验证现有压力调度是否足够，再决定是否调整归档预算或commitment轮换。当前实现已有字节压力探针，不能把方向表述成完全缺少该机制。设备较忙，盲目提高后台并发可能挤占同步；当前也没有足够证据估计强制压缩能回收多少GiB。
