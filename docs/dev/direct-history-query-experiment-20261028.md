## 变更与对照隔离

1. 为不可变 manifest 编译历史/访问器配对身份表，按每个未解决键的倒排候选游标
   合并访问源。某键找到权威结果后立即退出候选合并，避免高频键继续拖着缺失键
   遍历所有未来段。未知、更换、未覆盖与不支持的源保留回退；路由字节仍每请求认证。
2. 补齐独立 history 副本的辅助 posting 尾部。严格从已有 frontier+1 追加到固定
   HEAD，只改辅助索引；权威状态和冷段引用不变。此项是实验条件，尚未实现为线上
   持续无积压策略。不能将组合收益说成只替换 reader 的收益。
3. KV 多键查询先合并原始 posting 候选块，再解码权威修复行验证 owner、generation、
   domain、完整 key、Tx；碰撞/失效候选继续重试。每个候选块只做一次批量校验。
4. 额外试验在一个 pinned 请求内缓存权威块解码，16MiB / 32,768 行 / 64 块上限。
   只保留 owning 解码结果，对回调克隆缓冲区，保留提前停止和错误顺序。
   该试验没有改善近 HEAD 延迟，不同轮次的生产背景发生切换；该改动已撤回，单独保留试验结果。

曾尝试仅放开 hot-only 预取，近 HEAD 延迟没有改善，已撤回。早期试验按 256 块
对齐重建 posting 的假设不正确（256 是每帧键出现次数），该副本不纳入最终结果；
最终对照使用从准确旧 frontier+1 追加的新副本。

## 实测结果

选定阶段共 44 个 HTTP 请求，剔除 1 个读取集合发现请求，43 个正式请求的返回值
全部一致。其生产背景在阶段内始终是 PID 20471 / 3e456e75。缓存试验发生在
另一生产背景 PID 13633 / 4486cfb6，内部也稳定，单独保留而不合并统计。

| 场景 | 基准/条件 | 新方案实测 |
| --- | --- | --- |
| 9M 私有冷历史页首次查询 | 旧 reader + 部分路由：19.805610、20.041820 s | 完整路由 + 直接候选游标 + 补齐热 posting：1.693848、1.503297 s |
| 9M 真正重复热查（read_bytes=0） | 同一新输入 | 0.905472–0.928981 s，n=4，中位 0.923269 s |
| 35M 重复热查（read_bytes=0） | 同一新输入 | 1.501199–2.020606 s，n=3，中位 1.718441 s |
| 近 HEAD，保留原辅助索引状态 | 新 reader + 完整冷路由 | 0.218444、0.229674 s |
| 近 HEAD，补齐热 posting 后 | 同一新 reader | 0.932413–1.223783 s，n=3，中位 0.959327 s |

旧组合第二次仍产生读盘，不将其冒充完全热缓存基准。

## 剩余瓶颈与验收结论

仍未达到稳定亚秒冷查，35M 热查也仍是秒级，组合方案暂不作为发布通过结果。
但“大范围探测不可避免”已被实验否定：直接定位与覆盖补齐使冷查 I/O 显著下降。

选定 reader 的额外 15 s CPU profile 在计时样本外采集。9M 剩余 CPU 的主要位置：
候选计划生成累计 37.26%，其中 route column/map 查找累计 32.94%；路由加载累计
25.80%，SHA256 累计 19.78%。这些是嵌套累计比例，不能相加。具体大头已经从
遍历数千个 seg/kv 转为候选计划构造和路由认证。需要在同一 pinned 请求内复用
覆盖向量/候选映射、复用已认证路由视图；若重构格式，再考虑页级校验和全局键目录，
减少每请求读取、复制、哈希约 90 MB 路由数据。保持缺失/未知源的保守回退。

近 HEAD 补齐 posting 后，read_bytes=0、读调用仅 2 次，但累计分配从约 42.3 MB
升至约 793.9 MB，CPU 从约 0.224 s 升至约 0.962 s。该回退位于内存/CPU 索引
访问路径，继续调磁盘预读没有针对性。hot-only 预取和请求块缓存都没消除它，已撤回。
尚未独立采集近 HEAD 的分配 profile，因此不把上述 9M CPU profile 的函数比例
套用到近 HEAD。下一次应先定位并限制热 posting 查找的目录/结果展开，再决定是否
将热端改为能直接按 key+Tx 前驱/后继定位的索引，防止补齐索引反而拖慢短跨度查询。

## 正确性和边界

本地定向测试、race 和 vet 通过，覆盖候选未知源/替换源、频繁键退出、失效 posting、
修复行、重复键、缓冲区所有权、嵌套读取、取消、缓存容量回退和错误顺序。服务器
Sapling 原生构建和 HTTP 返回值逐项对照。遵循性能优先要求，没有重复全量 MuHash
重算和全量快照恢复；本轮不声称获得新的全量校验回执。
