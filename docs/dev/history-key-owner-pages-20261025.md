本轮完成账户和 AccountAssetV2 重复地址压缩，代码仅在本地提交 `f42f53ae`、`6a96f60c`。
**未推送、未部署、未重启或修改生产数据库。** 同一冻结 cohort 的 `.kv` 文件长度
126,009,832,509 → 119,501,234,404 B，净省 **6,508,598,105 B（5.16515%）**。
完整 HTTP 历史 `eth_call` 返回值全部正确；冷缓存历史查询中位数变化约 −1.02% 至 +1.28%，

## 格式与读取方式

在原有相邻前缀压缩上增加单个 accessor 内共享的 20 字节地址字典，账户及多个 KV 域
使用同一排序编号；AccountAssetV2 的资产标识后缀保留。字典按 128 个地址分页，键页
用 4 字节编号替换重复地址，解码后恢复完整规范键。键 ID、顺序、逻辑键摘要、状态值、
`.seg`、`.idx`、V9 多次变化 posting 和共享定位表保持不变。字典保存在同一个 `.kv`
内，不增加外部依赖或修改 MuHash 状态编码。

每个压缩键页最多引用四个地址页。不划算的页保留普通编码；整个文件扣除地址数据、
目录、CRC、footer 后不节省则逐字节输出 V9。小文件、通用短键和超过 1,048,576 个地址
的文件回退 V9。新增读取量有界：目录仅合并相近项，四个引用页最坏读取 234 B 目录；
地址 payload 最多 10,752 B/键页，相邻 payload 合并另受 64 KiB 上限约束。最初实现会
把较远的目录项一并读入，最终提交
`6a96f60c` 收紧该规则；不改变任何输出字节。三个真实文件修改前后 SHA 和元数据完全相同。

## 完整 HTTP `eth_call`

同一完整固定副本、同一 Linux amd64 / Go 1.25.5、相同 512 MiB hot/history cache、
128 MiB latest cache、GOMAXPROCS=2、GOMEMLIMIT=3 GiB；原版 V9 与最终 V10 读取程序对比。
未修改的完整 HTTP host 驱动 SHA256 为
`10e6015af7666bf83b5c405543681c368b7537f428b8278a3344f0312aacd3bf`。
原始 before-image oracle 返回预期 6/7/63/207/225/225/225，并由 V9 存储交叉核对。
合约 `0xa4997124a328a4615eab437cede31da47a31b375`、calldata `0x9fa6a6e3`。

每个高度每个版本：暖缓存 10 次、独立进程但 OS 页缓存不控制 3 次、私有文件 OS 冷缓存
独立进程 4 次，合计 238 个计时请求。另含发现、预热和追踪等 48 个响应，共 286 个，
全部结果与 oracle 相同、无 RPC 错误。CPU profile 负载另计 V9 90 次 / V10 91 次，亦全部正确。
启动时间不计入请求延迟；trace/profile 不混入正常计时。

OS 冷缓存只对经过独立 inode、完整 SHA 核对的私有文件执行逐文件回收，不使用全局
`drop_caches`。每个版本 2,254 个私有读集文件，56 个启动前驻留证明最大比例
0.0000538%，均小于 1%。启动本身会加载数据，因此是“启动前页缓存冷”的完整请求，

### 额外读取与剩余瓶颈

V10 为共享地址多做少量有界读取，不能把物理节省称为零开销。单次 OS 冷追踪中 9M
总数据库读取 1,848 → 1,876 次，22,556,639 → 22,641,778 B，增加 28 次 / 85,139 B。
`.sst` 始终 1,704 次 / 15,738,286 B，`.route` 始终 9 次 / 4,726,295 B，
`.seg` 始终 59 次 / 1,325,060 B。新增成本来自 `.kv` 共享字典，整体读取字节 +0.377%。
最早历史点增加 58 次 / 162,394 B。冷 9M 请求物理读取中位数约 29.008 → 29.127 MB，
分配约 31.932 → 32.095 MB；暖 9M 分配约 24.258 → 24.424 MB。

9M 最终 V10 CPU profile：热 history `iterateHistoryOwnerSpans` 累计 **45.29%**，
`FirstStateDomainChangesContext` 累计 31.02%；Snappy 解码 flat 19.33%、SHA256 flat
13.68%、Blake2b flat 11.99%。这些项存在调用嵌套，不能把累计占比直接相加。
V9 热尾累计 44.39%，整体结构相近，V10 地址解码没有进入 top35；后者只表示本次有限
profile 中不是显著节点，不等于开销为零。

下一步性能优先级仍是热 history owner spans 的读取/解码和路由校验开销。可考虑
按源身份绑定、有明确预算的已验证 owner 页/路由页复用，减少重复解码；需要另做污染、
取消、generation 切换及并发测试，不能跳过校验换性能。本轮未修改这些路径。构建端
增加地址扫描及两份候选键页编码，本轮验证了实际产物
与读取性能，未把离线转换耗时冒充线上冷发布吞吐；写入/压实代价仍需独立负载验证。
