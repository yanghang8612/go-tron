# 热 history 尾部与冷库小块读取优化（2026-10-21）

9M 固定历史调用的完整 HTTP 中位数，暖缓存由 **236.375 ms 降至 167.230 ms（减少 29.25%）**，独立副本 OS 冷缓存由 **1,616.219 ms 降至 835.388 ms（减少 48.31%）**。本轮 154 个 HTTP 返回值全部正确。此结果是离线代码及辅助索引的联合对照，不是线上 9030ce7a 的直接 A/B；小样本亚秒结果不能保证生产 p95 或所有合约都低于一秒。

候选源码冻结为 `4d34e751f0d37add20451ca9aae2d68e0c930b6e`。没有推送、部署、重启线上服务，未删除或重建生产库，也未恢复定时巡检。

## 实际瓶颈与失败试验

第一轮 `d2e41fc5` 尝试溢出 owner 的首次变化摘要和按 OS 页对齐的物理缓存。154 次返回值正确，但 9M 暖缓存由 241.123 ms 变为 242.319 ms，OS 冷由 1,623.054 ms 变为 1,727.857 ms，未达到目标。保留这一轮全部数据，不把减少 syscall 数直接当作加速。

继续用测试专用诊断副本查明：

- 同一请求分别为 System 和目标合约完整扫描 **11,817,531..11,818,192，共 662 块**。原完整行缓存仅约 919 KB，未溢出，所以溢出摘要没有解决实测重复扫描。
- 208 次冷源打开中，**200 次来自同一合约的 ContractStorage**，18 次为系统动态属性；文件可以被不同查询重复打开。这解释了为何账户/系统键路由已优化后仍有大量随机读取。
- 第一轮 `.kv` 调用由 2,874 次减少到 1,977 次，但返回字节由 4,424,857 B 增至 7,250,478 B。4 KiB 目录从非对齐偏移开始，按 OS 页向下取整反而拆成两次读取；8/12/36/120 B 小头部也被放大。

第一轮 CPU 剖析约 70.64% 累计 CPU 落在 owner tail 迭代，68.98% 在底层 owner tail，67.93% 在 borrowed block decoder。比例相互包含，不能相加。该轮全量 MuHash 尚未启动就被最终版本的审计替代，不能称第一轮完成了全量审计。诊断 profile 原始采集成功，首次文本渲染因缺少 Go 缓存环境失败，补齐环境后恢复；原失败和恢复结果均保留。

## 最终改动与正确性边界

1. **在一次必要的完整热尾扫描中收集已知 owner。** `PrefetchExecutionAt` 登记 System、目标合约和非空 caller，不产生 I/O。扫描先按 sequence 应用 repair，再选择 owner。同请求共享 8 MiB / 16,384 行 / 16 owner 上限；只有完整成功扫描才能发布行或缺失证明。提前命中、取消、损坏、回调错误不发布；溢出或未登记 owner 保留权威回退。首次变化摘要仍只用于精确相同的 block/transaction 窗口，不借助 legacy TxNum 单调性假设。通用历史迭代仍返回完整行。
2. **按实际读取偏移合并小读取。** 每次打开最多保留八个 4 KiB 窗口。accessor 前缀限 128 B，非对齐目录按请求偏移填充；segment 头部使用 4 KiB 前缀。较大读取直接传递。缓存绑定同一个打开的描述符，关闭即归还缓冲；失败填充使旧窗口失效，命中仍检查取消。压缩帧、字典、posting、CRC、完整 owner/key 的验证保持原路径。
3. **增加 ContractStorage 的 owner/generation/domain 路由。** V2 辅助对象按 31 B 规范前缀去重 slot，只排除该完整前缀在某配对中从未变化的段，不直接返回 slot。覆盖绑定已认证 history/accessor 的完整身份；替换源、未覆盖源及超预算源均回退。V1 没有 Storage 覆盖，缺失不能当作 Storage 不存在；构造器不能把 V1 列直接冒充 V2，必须重新认证字典。严格验证逐对重新构建 membership。

这些改动不改变规范状态键值、MuHash 输入、规范历史记录、冷发布/清理前沿或交易语义。V2 是新辅助对象，旧二进制不能直接读取它；新读取器同时接受 V1/V2。辅助索引可以从现有规范数据重新构建，无需仅为这项优化从创世同步。此轮输入此前已转换为小头部冷段布局，因此不能把结果直接承诺给保留旧布局的生产库。

## 索引成本

最终覆盖 **4,609 对**冷源，**16,669 个 Storage 前缀、16,703 个总键**，595,112 条 Storage membership。73 个有界批次，构建 **191.780 s**，含严格全量字典复核 **370.197 s**。新活跃对象 **1,515,200 B**，相对 V1 的 158,489 B 增加 **1,356,711 B**；这是活跃文件长度，不是服务器净磁盘增量，副本及退休文件仍保留。

构造每批至多 64 新源，完整对象有 64 MiB / 1M 键等预算，超限不发布错误缺失证明。此副本的 1.5 MB 成本不能外推到所有合约/完整主网未来规模；若触及预算，应采用有认证的分页路由并单独验证构建和增长成本。

## 最终验证与剩余开销

本地与服务器 Linux/Sapling 的 rawdb/state/snapshots 完整包测试、针对性 race、core/CLI 的 MuHash/ArchiveQuery/快照/恢复回归、vet 和构建均通过。最终 `4d34e751` 在 V2 派生副本全量重算 MuHash，耗时 889.43 s；三族源行数 **3,484,117 / 481 / 141,418,493**，重算根与固定捕获完全一致。

最终独立 20 秒暖 CPU profile 中，约 **58.36% 累计 CPU 在热 owner tail、55.77% 在 shared-pack borrowed decoder**，Snappy 解码 14.73%；这些比例互相包含。`loadSystemHistoryRouting` 约 9.35%，`latestSegmentRef` 约 9.05%，全部 SHA256 Write 约 11.94%（还包括其他来源，不能全算给路由）。因此下一步的大头仍是：

1. **避免首次热尾扫描解码无关 owner 的整个 shared pack。** 设计绑定 pinned sequence 的 owner/row-range 索引或可独立解压的 owner 帧，先证明覆盖再跳过；repair 覆盖、非单调 TxNum 和未知/部分覆盖仍保留全扫描。当前请求级复用已经消除了已知两次完整扫描的重复部分，不能再假定重复缓存会消除首次扫描。
2. **在一次固定 manifest/read lease 中复用已认证路由与范围查找。** 本请求仍读认证路由多次；后续应保留文件替换/损坏校验，并把清单定位从反复扫描改成有界索引。随着全主网覆盖增长，再评估分页认证，避免整体路由根持续放大。

这两项是根据剩余剖析提出的后续方案，未实现、未推送，未声称已有收益。所有实验重任务串行执行，资源样本中的服务器 MemAvailable 最低约 **25.99 GiB**；实验单元使用 5 GiB memory cgroup 上限（含文件页缓存，不等同进程 RSS）。有界采样及实验单元已结束。
