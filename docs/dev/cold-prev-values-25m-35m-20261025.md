## 下一步应压缩什么

1. **先实验账户旧值的有界差分/共享字段。** 账户载荷 153.529 GB 是最大的候选面。当前账户已经使用紧凑存储编码，地址、默认字段等已有省略；不能再次把“原始 protobuf/完整地址去重”算成新增收益。本次未测同键相邻版本可重复的字段比例。下一步应扫描相邻版本的规范字节差异，试页内检查点加有界差分，保留未知字段和原字节，限制一次随机查询的还原链长，再用同一副本做完整 HTTP A/B。
2. **旧值数值紧凑化应单独测外层压缩后的净收益。** ContractStorage 的 918,136,573 个存在旧值全部为 32 B，共 29,380,370,336 B；去前导零后有效字节 6,459,871,687 B，前导零共 **22,920,498,649 B**。AccountAssetV2 的 555,554,421 个存在旧值全部为 8 B，有效字节 2,106,754,884 B，前导零 **2,337,680,484 B**。这些只是编码前机会，**不能声称还能回收 25.258 GB**：外层 codec 已压缩零串，必须计入标记、长度、目录及重编码成本。`latest` 的紧凑存在封装不会自动改变 `.seg` 直接保存的规范 `Prev`。
3. **记录边框也是候选。** 每条重复 8 B TxNum，目标范围合计 44,880,438,000 B 逻辑字段。本轮 V11 仅消除 `.kv` 多次变化 posting 的 TxNum；没有更改 `.seg`。若后续把 `.seg` TxNum 也映射到共享区间，应逐页认证、可独立还原，并重做严格历史恢复/导入验证；不能把逻辑字段长度等同物理节省。
4. **不要为了空间恢复无限回溯。** `.seg` 旧值压缩涉及完整历史状态；大包跨键扫描、长版本链或以扫描数据体恢复 offset 会重新引入秒级延迟。候选必须保留有界定位和独立页校验，并与当前 V11 的 `.kv` 空间收益分开核算。

以上是下一阶段方案，尚未实现或部署；本轮只实现共享交易区间 posting，并补齐本次 census。
