# 多次变化 posting 共享 offset 页：V9 离线验收

范围：只在独立工作树及固定副本实现、验证；本次不推送、不部署、不重启线上节点，不转换线上库。

## 结果与范围

V9 将多次变化 posting 中的直接逻辑 offset 移到全段共享分页表，保留 TxNum 与记录 ordinal。完整 19,949 个 accessor 的文件长由 **143,407,842,868 → 126,009,832,509 B**，净少 **17,398,010,359 B（12.131840%）**。这包含所有新增定位表、目录、校验和文件尾；不能把移除的 33.59 GB offset 全算作净收益，也不能外推整节点或后续高度。

同一完整 11,818,192 高度副本的完整 HTTP `eth_call` 没有证明整体提速：9M 热缓存约 131.992 → 127.228 ms，独立 OS 冷缓存约 782.726 → 799.946 ms；5M 热缓存有回退。空间收益成立，但不把本次格式优化描述为解决了完整 HTTP 慢查询。所有返回值、canonical MuHash 及实际恢复窗口核验通过。

## 格式及查询路径

- `.kv` accessor 独立升级至 V9；`.seg` 仍为 V6、`.idx` 独立 V8、before-image、字典键/ID/SHA、TxNum、ordinal、canonical 状态和 MuHash 元素编码不变。内联单次变化仍保留直接 offset。
- 多 posting 分帧只编码 TxNum 与 ordinal；共享定位表每 128 行一页，首 offset 为 48 位，后续正增量 varint。每页目录项为 12 B，CRC 绑定页号、定位项及内容；32 B 文件尾绑定记录数、长度和页大小。
- 先按 TxNum 选中变化，再解析选中的 ordinal。请求/迭代器内最多缓存 64 页；同一批查询复用 resolver，无跨请求、跨 generation 缓存。没有从 checkpoint 扫描 `.seg` 来找 offset。
- 生产构建按 ordinal 顺序写有界 scratch 文件，随既有物理 SHA、fsync 和发布闸门输出。完整验证顺序遍历定位表；联合导入将 locator 与权威 `.seg` 流的真实位置比较，并经 ETL 核对 key/TxNum/ordinal。单次变化的直接 offset 仍单独核对。CRC 和 SHA 重新计算后伪造 locator/inline tuple 的测试仍会被语义校验拒绝。
- 新读取器保留 V7/V8 显式读取路径；旧读取器不能读取 V9。本次没有线上迁移命令或启动自动转换。离线转换器只在测试中使用，有 128 MiB/16M 记录上限，不能当作已交付的生产迁移工具。

## 正确性

完整节点副本头高度 11,818,192，head TxNum 601,386,177，MuHash `8fbf149684146a59b1650b318a768f0edbae0c8c1c3ceb2c5c610129c10f76a5`。两侧由同一冻结物理输入派生；候选只替换 `.kv`，辅助路由 source ID 随文件物理 SHA 重绑定，并对成员关系做完整严格重建核验；冷/清理前沿不变。

- 全量扫描 144,903,091 个物理行，分源 3,484,117 / 481 / 141,418,493，重算 canonical MuHash 与固定根一致。物理行含失效 generation，不能当作全部 canonical 元素数；MuHash 本身也不能替代历史索引验证。
- 在 3,144,020、5M、9M 三个 20 块窗口实际恢复、读回，共 387 / 11,845 / 10,264 行（合计 22,496 行）及 60 个交易范围；恢复前后完整行流 SHA 一致。包级回归另覆盖导入、导出、构建、合并和恢复。这不是 11.8M 的全量快照导出/导入实验。
- V7/V8/V9 读取、0/1/127/128/129/4097 locator 边界、单/多次混合、溢出/截断、CRC、取消、流式构建、伪造 locator/inline tuple 联合拒绝测试通过。
- 本地及服务器 Sapling 环境的 rawdb、state、snapshots、core、CLI 五包完整测试、相关 race、vet 及服务器构建通过。1,076 个候选非测试 Go/Rust 源码 SHA 与本地已提交源码逐文件一致。

## 完整 HTTP eth_call

完整 loopback HTTP → JSON-RPC → TronBackend → TVM，不启动同步/P2P/发布/清理。合约 `0xa4997124a328a4615eab437cede31da47a31b375`，calldata `0x9fa6a6e3`；七个高度预期值为 6 / 7 / 63 / 207 / 225 / 225 / 225，来自原 full-row before-image oracle。两侧宿主 SHA 相同；GOMAXPROCS=2、GOMEMLIMIT=3GiB、hot/history 各 512 MiB、latest 128 MiB。

每侧每高度：热缓存 10 次、全新进程但不控制 OS 缓存 3 次、独立 inode 的 OS 冷缓存 4 次，共 **238 个计时请求**；另有发现、预热、trace 等 48 个检查，共 **286 个普通检查全部返回正确**。CPU profile 工作负载另计，不纳入延迟分布。

OS 冷输入的读取集合逐文件 SHA 与冻结源一致，且 inode 与原输入及线上独立；两侧可共享同一个已验证的实验专用 SST inode，样本顺序交错，逐次只对实验专用文件 fadvise。未清理全局 page cache。启动前 mincore 驻留比例均低于 1%，最大驻留比例为 0.0000776571%。进程启动耗时不计入 RPC；控制的是 OS 缓存，不是硬件设备缓存。

本次只验证这一个 TVM 调用路径及七个历史高度，不能代表其他合约、重存储扫描、并发请求、当前 35M 或生产尾延迟。

请求窗口 trace（逐线程拼接 unfinished/resumed，只计两次 `/proc/self/io` 标记之间成功的 read/pread）显示新增间接读取的代价：9M `.kv` **58 → 74 次**，165,534 → 194,494 B，小于 256 B 的读取 18 → 27 次；最早高度 `.kv` 109 → 136 次、309,512 → 351,016 B。两侧 9M `.sst` 仍均为 1,704 次 / 15,738,286 B，`.route` 均为 9 次 / 4,726,295 B，`.seg` 均为 59 次 / 1,325,060 B。这里是逻辑系统调用读取，不是块设备物理读量；trace 请求不计入延迟表。

9M 热缓存的请求窗口资源中位数：CPU 131.423 → 126.726 ms，分配 24,261,444 → 24,256,568 B，syscr 128 → 144。OS 冷缓存 syscr 1,834 → 1,850，物理 `read_bytes` 28,655,616 → 29,007,812 B。进程多线程累计 CPU 与墙钟含义不同；这些资源窗口包含相关后台线程，不能把所有增量都精确归作一个函数。

候选 9M CPU profile：`PrefetchExecutionAt` 累计 78.61%，热尾 `iterateOwnerLocked` 48.32%、`iterateHistoryOwnerSpans` 45.15%，冷分支 `FirstStateDomainChangesContext` 31.49%。Snappy 解码平坦 19.50%，SHA256 AVX2 13.37%，Blake2b AVX2 12.87%。累计调用树存在父子重叠，不相加。这次没有修改热尾：`core/rawdb/state_history_owner_spans.go` 仍在选中 owner span 后先验证整个 pack 的 Blake2b，再 materialize / Snappy 解码完整 payload，最后才遍历选中行；冷路由和不可变段选择也仍有开销。

后续查询优化应优先验证热尾按 owner 独立可校验/解压的块布局、绑定 source ID 与生命周期的元数据复用，以及冷路由/段选择重复工作；若继续迭代 V9 点查，可测试目录项的有界批量读取，减少新增 locator 小读。不能直接省略完整性检查，或缓存其他 generation 的未命中结论。本次不额外实施这些结构改动。

空间方面，V9 剩余文件中压缩键页 **63.533 GB（50.42%）**，多 posting **44.617 GB（35.41%）**，locator **16.287 GB（12.93%）**。后续大头已转为键页及 TxNum/ordinal；共享字典或交易游程定位需要另做空间/查询对照，前一轮的静态预算不能当作已实现收益。
