# 冷库慢查询后续优化：日志地址与热尾部复用

本轮完成读路径修改，并在本地与服务器独立副本验收。生产继续使用
`9030ce7a31016491ece014ac76e5656ec149417e`；本轮没有推送、上线、重启、迁移格式或清库。
现有 compact-v3 数据可直接续用。实现与验收源文件指纹见本页末尾证据。

慢查询主要成本已由前一轮线上 CPU profile 定位到未索引热尾部的整包 RLP 解码。
这轮消除无关行的对象分配和同一请求中的重复扫描，同时修复独立发现的日志地址漏结果。
冷段逐段打开、读取和校验仍有成本，下面的组件收益不能直接等同于整 RPC 收益。

- 日志筛选按 20 字节身份比较，段内和全局索引同时查询既有的 `00` 填充键、`41` 前缀键。
  保留原日志地址宽度、所有持久化字节、校验和、规范交易核对及 topic 交集；合并候选时去重。
  JSON-RPC 输入仍遵守原有 20 字节规则，未放宽对 21 字节输入的拒绝。
- 热尾部使用现有经过校验的借用式 decoder，所有行仍经过解析和校验，只复制请求地址相关的行。
  先应用正序号修复覆盖，再使用结果；修复把原行改成另一个地址时也能正确移除原匹配。
- 只在明确固定的 RPC MVCC 快照内缓存完整的地址/块区间扫描。可复用包含当前范围的扫描，
  TxNum、Seq、generation、domain、key 和冷热重叠比较仍由原 accessor 执行。
  最多 16 个地址、16,384 行、8 MiB 的载荷及行开销记账；这不是整个 RPC RSS 或单块解码临时内存上限。
  超预算沿当前扫描继续，并停止为该地址尝试缓存；不会为退回原路径再扫描一次。
- 正查询一旦命中便提前返回，不为填缓存扫描整个尾部；未完整扫描、取消或损坏的结果不发布覆盖断言。
  缓存不跨请求，不持有文件、额外快照或 manifest，不会把旧 generation 的不存在结论带到新快照。

128 个 pack × 每包 4,096 行，共 524,288 条人工 KV 历史；每次操作连续查询 8 次。
全部输入位于同一内存数据库，分别测量全尾部负查和首包命中，不涉及磁盘 I/O 或 HTTP。
每组 3 次 `-benchtime=1x`，下表是中位数，不是 p95。分配是 Go TotalAlloc，不是 RSS。

索引滞后还有明确的调度来源：`net/sync.go` 每 4,096 个导入块轮换会话、完成提交屏障后才唤醒派生索引 worker；
history 单次最多 4,096 块，最小 256 块。只降低最小块数无法让唤醒更频繁。
同一 9030 进程 06:08:50–06:47:51 UTC 的 40 个分钟样本，Finish 与 StateHistoryIndex 的采样差为
363–4,336 块，中位 2,513，呈现会话批次的波动。它不是某个 RPC 固定快照内的精确尾部长度。
这轮保持调度和内存参数不变；单独改变会话屏障还会改变提交节奏、ETL posting 帧及写放大，
需要同输入的同步吞吐和写入量对照，不能仅以缩短尾部为由直接缩小批次。
后续应先在本读路径上线后复测完整 RPC，分离剩余冷段校验与热尾部成本，再决定是否拆开 history 唤醒与会话屏障。
