## 物理格式启用情况

对固定目录全部冷 history/accessor 的头部 census：`.seg` 29,658 个全部为
`gtcblk01` V2；`.kv` V7 为 26,878 个、V11 为 2,780 个。此 census 单独记录
头部标识，不冒充每个 history payload 的全量认证。accessor 在全源严格路由核验中
另有完整物理 SHA256 校验。

生产参数是 `--history.compression-format=auto` 和
`--history.reference-container=false`。代码的 `auto` 普通输出选择 V2，
`auto-columns` 才选择 V5；本目录没有 V3/V4/V5 history 文件。
因此此前 V11 索引读写已用于部分源；列式旧值和共享容器在这个目录中尚未采用。
本次 V11 重复目录验证有直接栈与字节计数证据，旧值压缩算法不是本轮采样中已证明的主因。

## 本轮读取与构建优化

1. 在当前不可变 accessor 打开描述符内复用已完整验证的 framed header，
   避免打开、附加 history 及批量读取重复验证 V11 交易目录。关闭后丢弃，
   新打开仍重新认证；保留大小、取消、关闭、损坏检测及并发保护。
2. 大路由仍认证全部物理字节并验证所有编码行，仅保留请求需要的成员行，
   避免为一个合约 metadata 查询分配近百万键 map。部分视图不进入共享完整表缓存；
   未选择的键仍返回“不确定”，不得生成错误的缺失证明。
3. 轻量路由构建先将整个 exact accessor 与 manifest SHA256 核对并验证
   history 字典绑定，再定位所需 owner/generation/domain 范围，跳过无关 Shielded
   和槽位键解码。支持未来新键、新 generation 和 uint64 最大 generation；
   严格导入另用独立完整字典遍历核验全部成员，未用优化路径自证正确。

本轮没有再改变冷段格式、canonical 旧值、记录序号、交易范围、MuHash 元素或恢复编码。
轻量路由的 manifest kind、维护/校验/退休逻辑来自此前尚未发布的候选，仍需整体新读者支持。

## 测量与正确性边界

测量使用固定 canonical 对象、服务器 Go 1.25.5、GOMAXPROCS=2、GOMEMLIMIT=3GiB，
诊断单元 CPUQuota=200%、MemoryLimit=4GiB、Nice=15，I/O 设为空闲优先级。
进程首次、进程内热样本和独立文件 OS 冷缓存样本分组，跟踪样本不计入延迟统计。
OS 冷缓存只驱逐经 SHA256 与独立 inode 证明的私有测试文件；不使用全局 drop_caches。

此前 11.8M 一致状态副本已在清理中删除，用户确认没有其他副本。
本轮固定的不可变冷目录可以验证冷查询、行流和历史恢复，不能充当完整状态副本：
**本轮不能完成当前目录规模的完整 HTTP 新旧性能对照，也不能全量重算当前最新状态 MuHash。**
此前 11.8M 的全量 MuHash 回执只属于此前受测源码及副本，本轮不重复借用其结论。

本地最终 snapshots 全包、core/state/rawdb/core/jsonrpc 历史与 MuHash 相关测试、
race、vet 和构建通过；受测 13 个产品文件 SHA256 在测试前后保持一致。
服务器原生测试覆盖损坏、取消、选择视图缓存隔离、严格导入、签名目录恢复及恢复后 MuHash。
实物冷目录上的全源独立成员校验、历史行恢复和交错性能数据另附原始回执。

完整 HTTP 验收仍需要含 chaindata/history 的同一时间点状态快照。
在用户禁止启停服务的约束下，本轮不把活动文件复制当作一致副本，不声称已经证明端到端速度。

## 剩余主要路径

140 个系统预取项单独查询，候选后续中位数 278.922 ms、逻辑读取约 6.21 MB，
367 次读取系统调用。单个合约 metadata 项单独查询，候选后续中位数仍为
1.184 秒、逻辑读取约 402.90 MB、62,284 次读取调用；该项在固定冷区间返回空。
两个分组各只有 2 个后续样本，其时长不能严格相加或转换为整体墙钟百分比。
它们明确将剩余成本指向 metadata 缺失证明路径及未覆盖源读取。

补充单项 metadata 的 strace/CPU 跟踪，通过两次 `/proc/self/io` 读取标记界定
业务调用窗口，与 Manager 启动读取分开。本地解析 unfinished/resumed 调用并逐个
source-pair 比对，窗口中打开的路径集合恰好等于 4,058 个未覆盖源：

| 文件 | 独立文件数 / 打开次数 | read/pread 次数 | 返回的逻辑字节 |
|---|---:|---:|---:|
| 旧大路由 | 1 | 1 | 66,948,766 |
| `.kv` | 4,058 | 46,046 | 198,403,541 |
| `.seg` | 4,058 | 16,232 | 137,544,389 |

此跟踪的单项结果为 `[null]`，与独立基线相同。V2 打开/绑定 header、压缩目录和
key block 查找产生这些读取，尽管该合约 metadata 在整个目标冷区间没有变化。
该进程 CPU profile 覆盖 41.41 秒，采样 CPU 6.91 秒；`Syscall6` flat 2.79 秒，
zstd 解码核心 flat 0.38 秒；大路由选择解码累计 0.06 秒。
跟踪后的墙钟约 40 秒、物理读取约 1.057 GB，含 ptrace/profiling 干扰；
本补充仅执行私有文件 fadvise、没有重新测 mincore，**不计入前述正式冷缓存性能分组**。
系统调用耗时也不能直接当作无跟踪请求的精确阶段耗时。

下一阶段应优先把 ContractMetadata 与高基数 ContractStorage 路由分离并分页，
用经过源身份绑定、严格重建验证的覆盖证明跨过无变化冷段，同时限制所需认证页的大小。
当前选择解码仅减少解码 map 的分配，仍整读并认证 66.95 MB 文件；
header 复用也没有消除未覆盖源的打开和随机页读取。
全源路由更新需要避开单个混合表的 64 MiB 上限，并按源替换/退休维护正确覆盖。
这些后续格式与维护改造尚未实现，本轮没有宣称冷启动或完整 HTTP 已经解决。
