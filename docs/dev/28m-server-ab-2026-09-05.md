## 连接恢复后的顺序

1. 确认 hostname、gtron/gtron-nile 的 active/substate、PID/重启次数、正式 API 的高度和同步进度；读取实际 listeners、CPU/内存、磁盘空间与 I/O。检查配置时隐藏私钥等字段。
2. 先列 `/data/gtron` 的备份目录和 manifest，确认高度、block hash、internal root、schema、生成方式及完整性。不能仅凭文件名或目录日期判断是 28M 一致快照；不能把运行中的 Pebble 目录普通复制当作一致备份。
3. 检查起点状态、TAPOS 所需数据、冷数据路径及完整后续输入区间。保留原备份，创建新测试副本，不用硬链接共享可写数据库文件。空间或输入不足时记录具体缺口。
4. 保存旧新 binary/source/patch/Rust hashes、Go 版本、构建标签和相同运行配置。先在旧版副本完成短区间，确认该备份兼容基线源码，然后在新版同起点副本运行相同输入。
5. 每次都从原 checkpoint 的新副本开始，顺序运行 A/B；记录其它服务和磁盘竞争情况。只有隔离负载后的重复测试才用于归因性能。
6. 比较成功进程退出状态、审计 start/block 记录、internal roots、每 tx 历史摘要、tx-range 和本次执行产生的回执摘要。完成记录中的耗时另作比较，不把两份审计文件直接逐字节 diff，因为耗时必然不同。
7. 首轮用短区间验证正确性；通过后延长到代表性 28M 区间，并记录 CPU profile、wall time、RSS、I/O 和后台债务。发现状态/回执/历史差异立即停止扩大测试，保留失败副本和日志。

## 计时边界

离线 stored replay 每 1,000 块建立一个 staged range，包含 commit settle、末尾 buffer flush 和 sync；其 session、read-ahead 和后台维护形状与在线长时间同步不完全相同。pipeline wall 与含审计/关闭的总耗时分别记录，外层再用 `/usr/bin/time -v` 收集完整进程时间和峰值 RSS。结果应标为离线重放，不直接声称线上同步达到同幅提速。
