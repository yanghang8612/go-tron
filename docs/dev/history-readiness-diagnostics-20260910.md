# 归档资源观测与状态读取诊断（2026-09-10）

## 问题与本轮范围

部署后 14:01–14:06 连续五分钟的 21 个样本中，CPU parallel probe 有 9 次 known/ready=0，13 次冷构建仅 5 次采用状态/事件并行。源码确认两个探针均依赖调用采样；CPU 回调还会被存储准入短路。调用间隔超过 30 秒时只能重新建立基线，冷却或长任务因此可能反复错过可用资源观测。

本轮把 CPU/设备基线刷新接入节点生命周期：启动开始采样，每次有界读取完成后等待 5 秒再采样，停止时取消并等待在途读取结束。归档消费者先停止，资源采样器随后停止，数据库最后关闭。保留调用时的新鲜 Pebble 压力读取，以及全部 CPU、cgroup、内存、设备、共享维护门条件和 5–30 秒有效采样区间。修正 CPU 缓存周期从读开始计时、可能使连续观测实际不足 5 秒的问题。

这一修复提高资源证据的新鲜度；不直接提高历史 duty、扩大批量或承诺净追赶速度。现有 20%/80% 等负荷反馈、恢复等待和硬保护继续决定是否及如何执行归档。上线验收同时关注资源未知比例、实际并行构建比例、导入/状态发布速度和积压变化。

## Commitment 缓存计数

现有五分钟样本中，深度 6/7 占前台 parent durable 读取约 95.7%。但 deep window 的 promotion 包含 flush/prefetch 引用，不能当作真实读复用；当前统计也无法区别 resident 比父快照新与无 resident。直接扩大缓存缺少证据。

本轮按原分支补充 resident 较新、无 resident、填充时全局版本已变化三类事件计数。计数在 reader 内累加，沿既有 Close 汇总，不额外查询缓存、不改变准入、大小、淘汰、父快照或借用内存语义。它们是探测/填充事件数，重查可重复计数，不是唯一 key 或逻辑请求数。

SLOAD 的主要成本在数据库点查，移除一次 32 字节复制不是当前主要收益来源。保留现有策略；后续依据新增版本原因计数，以及按域区分的 overlay/cache/durable 样本，设计同输入缓存策略回放。所有后续优化仍须保留 dirty overlay、generation、存在零值与缺失、读集和父快照一致性。

## 资源与性能解释

CPU/设备观测本窗口均 41/41 点 known，CPU ready 也均为 1，资源硬停标志均为 0。但历史 duty 在 27 点为 20%、12 点为 80%、2 点为 90%；后半段仍有 15/21 点处于 20%。因此后续应分析负荷反馈与归档/正文/索引维护的实际交互，不能把 CPU 空闲直接等同于适合提高 duty。

源码 `history_load.go` 的 level 1/2/3 分别对应本次观测到的 20%/80%/90%。level 1 来自存储压力条件或恢复滞后；所有设备 await 都低于其设备压力条件所需的 5ms，write stall 计数也无增加，不能仅因 busy 接近 100% 就归因为磁盘饱和。level 1 点的预算 compaction debt 为 2.33–4.29GiB，但现有指标缺少 L0 sublevels、debtRises/good 和具体分支原因，尚不能把每次降级都归因为压缩债务上升。

设备预算观测的 await 为 0.711–1.217ms，busy 66.8%–99.7%，平均队列约 2.77–8.03；L0 表 23–91，Pebble estimateDebt 约 1.86–4.24GiB。15:05 的 RSS 约 16.21GiB、高水位 16.97GiB，低于保持不变的 40GiB 限制；数据盘剩余约 2.28TiB，空间保护检查通过。最后 1,500 行日志未命中 code rejection、ERROR、CRIT、panic、fatal；这是有界检查。

## 接下来的优化方向

1. **先稳定归档净追赶。** 补齐 level 1 原因位、L0/sublevel 阈值、debtRises/good 和观测时间，区分压缩债务与恢复滞后；同时测量维护任务持有共享 gate 的时间，再以固定负荷比较状态发布、正文和索引的协调策略。结合前台 TPS/延迟验收，不直接放大 duty 或撤销保护。另一个有证据的入口是减少重复 manifest 加载、解码与规划：本窗口 level 1 批次 metadata 约 1.105–1.406 秒，占 recovery_cost 中位值约 28.5%；20% duty 对工作计费形成约四倍恢复等待，减少真实工作可同时缩短恢复，无须修改计费语义。
2. **针对深度 6/7 的真实重复读取优化缓存。** 区分 no_resident 的 probation/epoch 拒绝、容量淘汰及淘汰后再读距离，拆开 foreground、prefetch、flush 的引用来源。确认高频再读后，在固定 512MiB 总预算下做单项本地回放，保留 snapshot/generation/overlay 语义。
3. **独立拆分 SLOAD 数据库读取与归档 manifest 成本。** Commitment 指标不能代表 ContractStorage；先按域统计 overlay/base hit/durable found/missing，再评估点查和 manifest 解码/重复读取。真实哈希拒绝若再次发生，使用本轮部署的来源、上下文和限长调用链定位，避免先改校验语义。

完整原始请求、前后对照、后半段、缓存与哈希独立复核分别在证据目录的 `comparison.json`、`after-analysis.json`、`cache-after-analysis.{py,json,md}`、`hash-after-analysis.{json,md}`。服务器 prepared/activation 原件保留在 release 目录；本地 `deployment-transcription.json` 明确标记为认证终端输出转录，不冒充服务器原始日志。
