## 改动依据

- 整批共用 route 覆盖与列号到 manifest 行号的转换，避免每个系统键重新做
  全冷段 map 查找。各键仍各自持有游标，已解决键及时退出合并。
- 一个历史 reader 保留最多 64MiB、8 个已认证的路由字节视图。constructor 和
  SetContext 都创建全新 scope；精确 dir+SegmentRef 绑定，不缓存读取错误/半成品，
  独立请求仍重新认证当前字节。大对象可在字节压力下替换较小对象，小对象不能
  挤掉更大的认证成本。解码器继续做完整结构校验，权威行匹配规则不变。
- posting 候选遍历复用最多 256 项的帧缓冲区，超过查询上界的帧不再解码。
  owning 解码接口不变，继续支持现有重叠帧和所有 varint/溢出/尾随字节检查。
  本地基准：每帧 2048 B / 1 alloc → 0 B / 0 alloc。
- 对有 owner-tail 缓存、已 pinned 且存在 stage 元数据的 <=16 块窗口，直接走
  原有权威变化包扫描。较长、未 pinned、无 stage 的查询保留索引路径。
  所有 Tx、owner、generation、domain、key 和修复行检查完全沿用。

首轮 `4466dca6` 已将近 HEAD 分配从约 794MB 降至约 43MB，但耗时仍约 0.8s。
因此最后补入短窗口成本选择；最终结论只依据新一轮 `query-plan-scope-final`。

## 最终实测

最终 36 个正式完整 HTTP 请求返回值全部与基准一致，9M 返回整数 207。
固定 HEAD/Tx/root、冷页零驻留与实际文件集合逐项匹配。阶段内线上背景始终是
PID 16604、启动 2026-10-28 10:01:31 UTC、版本 4486cfb6，本任务没有启停服务。

| 完整 HTTP 场景 | 同轮基准 9a9de233 | 新实现 a99fe47d | 新/旧样本数 |
| --- | ---: | ---: | ---: |
| 9M 私有冷历史页首次查询 | 1.371–1.420 s，中位 1.396 s | 1.160–1.219 s，中位 1.189 s | 2 / 2 |
| 9M 热查，read_bytes=0 | 0.869–1.042 s，中位 0.893 s | 0.545–0.689 s，中位 0.634 s | 4 / 4 |
| 9M 冷查后第二次，read_bytes=0 | 中位 0.870 s | 中位 0.609 s | 2 / 2 |
| 35M 热查，read_bytes=0 | 中位 1.586 s | 中位 1.414 s | 3 / 2 |
| 近 HEAD 热查，read_bytes=0 | 中位 0.965 s | 0.201–0.218 s，中位 0.208 s | 3 / 2 |

9M 冷查中位降低 14.77%，9M 热查中位降低 28.94%，近 HEAD 中位降低 78.46%
（4.64 倍）。近 HEAD 累计分配从 793,909,484 B 降至 42,212,904 B，下降 94.68%，
CPU 中位从 1.0362 s 降至 0.2073 s；原来约 0.22 s 的短跨度性能已恢复。
9M 冷查实际读盘仍约 109.55 MB、3937 次读调用、636 个文件，改进主要来自 CPU
路径。不能将旧部分路由输入的 20 s 或其他环境的 43.8/69 s 混入本轮倍数。

35M 仍未解决：本轮新版本单次热查仍读取约 638 MB 到用户空间、94,521 次读调用，
累计分配约 1.104 GB；read_bytes=0 表明该热查不是物理磁盘等待主导。
该高度的小样本只支持“仍是秒级”的结论，不将约 11% 中位变化说成稳定显著增益。
9M 冷查也尚未达到稳定亚秒，未测 35M 的受控冷页首次查询。

## 下一大头的精确辅助对象统计

这里必须更正“完整路由”的表述：完整的是 62 条轻量系统路由，记录了 32,036 个
源 ID，与当前冷源总数一致；通用大路由只有 25,600 个源 ID，Tx 上界 3,006,279,261，
而冷段上界是 4,063,356,397。源 ID 数量不替代逐一配对校验，不能据此虚构精确的
有效覆盖百分比；其范围之外没有这个对象提供的否定证据。

完整读取并核对 SHA256 的单个大路由对象为 66,948,766 B，占 64MiB 上限的 99.76%。
其中 header/source 表 819,240 B；59 条 system 记录 56,058 B；
951,110 条 ContractStorage 前缀记录 66,073,468 B，占整个文件 98.69%。
这些前缀记录的 membership payload 为 29,931,288 B，余下约 36.14 MB 是键和逐行
头部；其中 947,583 条为稀疏表示、3527 条为密集表示。此对象没有 ContractMetadata
记录，不能将其大头错误归因于合约 metadata。

下一步应把 ContractStorage 前缀路由改为带页级认证的随机查找目录，压缩重复的
flat/domain/generation 字段和稀疏源序号，并补齐更晚的源。这样同时处理首次查询
整包读/哈希，以及缺乏否定路由时的回退读取。该方案尚未实现、未在本轮声称收益；
35M 的 94,521 次读取仍需按具体源/页进一步归因。

## 正确性与限制

本地定向测试、race、vet 通过。覆盖反序 route 列、窗口、未覆盖源、
请求间物理文件篡改检测、同请求已认证读视图、引用/目录隔离、取消、并发与预算，
以及 posting 帧 owning/借用解码一致性、重叠帧、损坏帧、修复行、重复键和 Tx 切口。
短窗口同时比较单键与多键的权威行 oracle，并断言不访问 posting 前缀。

不改持久化格式、MuHash 更新或快照恢复写入路径；本轮未重复全量 MuHash 重算
或全量快照恢复，固定 HEAD/root 元数据一致不是新的全量状态校验回执。
