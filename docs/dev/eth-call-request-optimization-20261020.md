# 完整 HTTP eth_call：请求缓存、冷段合批与目录读取

本轮修改只在本地和固定副本运行。未推送、未部署、未重启生产服务，数据库格式和 MuHash 元素编码没有修改。性能、固定副本完整 MuHash 和独立 before-image oracle 复核均已完成，原始证据已下载并通过本地校验。

## 实现与边界

基线为 `4e6978dd`，候选为 `b6db66fcbde2d17f4b8fca099e5fd642e4435308`。源码中的 Go/Rust/module 文件、相同 HTTP 测试宿主、Linux 原生二进制与 Sapling 静态库均保存 SHA256。

- 请求级 first-change 缓存只在显式 pinned KV 视图和确定的热历史范围中启用。键包含目标/头部 TxNum、完整 owner、generation、flat domain、KV domain、逻辑 key；缓存正常的存在和不存在结果，复制输入输出，不保存失败、取消或不完整批次。上限为 4096 项和 4 MiB 保留计费，计费含复制数据与估算对象开销，不是整个请求的 RSS 上限。
- 常量调用先合批解析 System/caller/contract 账户，再依据历史账户 envelope 的 generation 合批查询动态属性、两个 fork vote 和合约 metadata。slot 仍按 TVM 实际读取。预取失败后正常 demand read 仍负责校验与报错；取消继续传播。
- 冷库混合查询在每个相关 segment 中共用一次已验证的 segment/accessor 打开，保留最早 TxNum/Seq、CRC、字典和范围校验。相同 AccountID 但完整地址前缀不同的 owner 不会误合并。
- 相同 owner/generation/domain 和相同 inclusive 冷命中上界的热 KV 键继续共用一次尾部扫描。不同冷命中上界单独处理，保留冷热同一事务中的 Seq 比较。
- 只有 manifest 中存在与请求相交的冷历史段时才执行可选预取。无相交段只表示预取没有收益，不构成不存在证明，不跳过正常查询。这样避免纯热查询承担额外的预取扫描。
- V6 目录的 offset pair 与完整 CRC entry 合并读取；V7 在一次打开的批处理中最多保留八个 4 KiB 目录页，结束后释放。没有全局目录负缓存或文件句柄缓存。

## 固定输入与测量方法

复用此前采集的同一个不可变副本，未重新采集不同高度的数据：

| 项目 | 值 |
|---|---|

| MuHash | `8fbf149684146a59b1650b318a768f0edbae0c8c1c3ceb2c5c610129c10f76a5` |
| 可见逻辑行数：Account / Generation / KV | 3,484,117 / 481 / 141,418,493 |
| manifest generation | 5101 |
| history / hot Pebble cache | 各 512 MiB |
| latest cache / GOMEMLIMIT / GOMAXPROCS | 128 MiB / 3 GiB / 2 |
| 离线 HTTP 单元预算 | CPUQuota 200%，MemoryLimit 5 GiB，nice 15，ionice idle |

使用真实 `TronBackend → JSONRPCHandler → TVM → JSON` 的 loopback HTTP 服务。两个版本使用相同测试宿主，readonly 打开数据库，不运行导入、freezer、清理和 P2P。每次退出核对固定 HEAD 未变。

调用合约 `0xa4997124a328a4615eab437cede31da47a31b375`，calldata `0x9fa6a6e3`，from 省略、value 为 0。覆盖 3,144,020、3,144,021、5M、9M、HEAD−256、HEAD−1 和 latest；期望值分别为 6、7、63、207、225、225、225。

独立 before-image oracle 从已核验的 latest 状态出发，使用完整冷历史逻辑 key 遍历和原始热历史遍历折叠 before-images，不使用优化后的 first-seek、请求缓存或 TVM。它与候选共享数据及解码器，因此不是独立实现所有持久化 codec 的第二条链。

暖缓存每版本每高度 5 次，先 A/B 再 B/A；首次进程请求 3 次；新进程加 OS 冷缓存 2 次。发现、预热、strace、CPU profile 和计数器请求均排除在性能表外。这是受限预算下的串行实验，不是生产并发吞吐或 p95/p99 结论。

OS 冷实验只对已独立复制的实验 inode 执行 `posix_fadvise(DONTNEED)`，不使用系统 `drop_caches`。复用上轮实验副本的硬链接并为新读取路径补独立复制；检查其 inode 与原始采集文件不同、发现的所有读取文件均被覆盖，每轮启动前用 mincore 证明驻留比例低于 1%。

深历史暖缓存改善约 2.1–2.5 倍；OS 冷缓存改善约 7–10%，没有把首次冷读降至毫秒级。近头部基本持平，HEAD−1 的暖缓存中位数增加约 2.1ms，不能宣称所有高度均更快。原先无条件预取造成的明显纯热回退已排除；最终范围判断仍通过 `Manager.Manifest()` 复制 manifest，保留了约 2.8MB 分配和约 1–2ms 的近头部成本，后续可以用 pinned manifest 的只读范围提示消除这次复制。

| 条件 / 版本 | CPU ms | 分配 MB | read 类调用 | read 返回 MB | 物理读取 MB |
|---|---:|---:|---:|---:|---:|
| 暖 / 4e | 6,893.47 | 3,586.87 | 1,231,453.00 | 2,056.98 | 0.00 |
| 暖 / b6 | 2,745.13 | 1,406.46 | 173,059.00 | 893.03 | 0.00 |
| OS 冷 / 4e | 9,919.78 | 4,143.99 | 1,233,647.00 | 2,073.92 | 3,107.74 |
| OS 冷 / b6 | 5,509.99 | 1,957.22 | 174,659.50 | 905.09 | 2,181.63 |

这说明合批和目录页减少了约 86% 的读取调用，暖查询 CPU 和分配量下降约 60%。OS 冷查询仍需约 2.18GB 物理读取；其 CPU 约 5.51s、墙钟约 31.61s，主要剩余时间在 CPU 运行之外。结合物理读取和只读服务配置，可推断首次文件访问与 I/O 等待是冷读的重要限制；这些计数不能单独区分设备等待、调度和 CPU 配额等待。

独立 20 秒候选 CPU profile 中，BLAKE2b 占 flat CPU 约 23.3%，系统调用约 18.1%，Zstd 解码约 3.0%，Snappy 解码约 3.3%。这不是按相同调用数归一化的新旧 CPU 百分比对照：两个版本在 20 秒内完成的高度组合不同。每高度 CPU 收益以前表的请求窗口计数为准。

当前证据不支持把剩余慢查询主要归因于 Zstd 解压。进一步优化应优先减少跨冷段的否定查询和重复内容认证，而不是扩大旧的 header 缓存：一条返回 32 字节的查询仍产生约 17 万次读取、905MB 应用读入和 2.18GB 冷物理读取。

独立计数诊断还定位到剩余的具体调用：3,144,020 高度第二轮请求中，两个预取批次分别是 3 个账户和 141 个 KV 键，另有 1 个 demand slot。该次计数版 handler 共约 2,725ms，三个冷查询批次合计约 2,405ms（约 88.2%）；两个大批次分别约 1,057ms 与 1,347ms，仍反复对各自约 281.61MB 的压缩输入计算内容摘要；全请求共重验约 563.30MB。该轮 header 缓存有 4,223 个不同 key、8,447 次命中，零 miss、零 eviction，说明扩大 8,192 项缓存不能消除这部分重读和摘要工作。请求 memo 有 145 次命中，其中 117 次为否定命中，峰值保留计费仅 41,036 B。诊断计数版不进入性能表。

固定 manifest 中有 4,609 个 state-domain-change history 段，总文件长度 48,379,073,819 B；其中 4,440 个为 aggregationSteps=1，86 个为 2、12 个为 3、71 个为 4。大量单步小段使否定查询需要触达大量 segment/accessor 配对。这里统计的是整个固定 manifest，不能直接当作每个请求的实际触达数；具体查询计数见独立诊断。

针对性后续方案：先为 pinned manifest 提供不复制的范围提示，消除近头部的额外分配；在新的派生副本上先对照测试现有 history 段合并压实，再研究跨段 first-change 路由/存在性摘要，只有在完整覆盖与 segment/accessor 绑定验证成功后才允许跳段，失败继续走现有认证路径。大块输入缓冲区复用也可单独验证，用来减少约 GB 级的临时分配和 GC。所有方案都应继续在固定副本上进行消融对照，不能用 stat/mtime 代替当前内容校验。

## 正确性与限制

本地已运行 state/rawdb/snapshots 相关完整包、相关 race、vet 和构建；最后两次调整后重新运行 state 全包、相关 race/vet。服务器使用 Go 1.25.5、CGO/Sapling 构建并运行历史账户/存储/generation、MuHash、archive query、快照和 CLI restore 回归。

快照验证包括 `TestMuHashFreshSnapshotContinuesAcrossMaintenance`、`TestSnapshotRestoreMuHashFreshCLI`、恢复后冷链索引查询及合约重建 generation 测试。它们是实际 fixture/CLI 恢复回归；没有对完整 11,818,192 主网副本执行全量导出再恢复演练，不将两者混称。

固定副本新一轮完整 MuHash 折叠于 12:52:36–13:07:29 UTC 完成，耗时约 894 秒。Account / Generation / KV 三类源数据 SHA256、可见行数、HEAD hash、TxNum 与旧审计完全一致，MuHash 为上表的 `8fbf…76a5`。独立 oracle 再运行一次后，238 次主实验和 14 次计数诊断 HTTP 返回值全部匹配。

本地封存校验还核对了两个版本共 2,132 个生产 Go/Rust/module 文件、相同宿主、11,428 个实验私有文件的 inode 证明、28 份 mincore 回执和元数据/WAL 摘要。实验文件共 157,021,873,555 B；最大全部实验私有文件驻留比例为 5.737952009125639e-7，冷缓存条件在每轮启动前均通过。
