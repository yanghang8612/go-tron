# 历史正文与热历史：业务类型、积压和 Erigon 对照

2026-09-07。保持停机维护 hold；没有启动 gtron、恢复同步、变更 MySQL 或生产数据格式。
本次新增的是独立只读诊断程序、隔离实验目录中的程序及报告。

## 两个大头保存的是什么

`state-snapshots/history/state-domain-change-*.seg` 保存已经转冷的**状态变更前的值**，
包括 keyID、变更 txNum、原值是否存在及原值正文，通过配套 `.kv` 字典关联完整 domain/key。`chaindata` 的
`state-changeset-v2-` 保存尚未转冷的同类历史，按区块打包，读取时还要应用 repair 行。
二者主要是同一种业务历史在不同时间范围的存放位置；不能把 history `.seg` 理解为区块正文。
区块/交易及其索引另有 hot 前缀和 ancient 文件。

上次目录实测：history `.seg` 共 **804.50 GiB**，占 state-snapshots **81.35%**；
热 changeset 的 SST 范围估算 **1,260.77 GiB**，占 chaindata **87.59%**。
前者是物理分配，后者是范围估算，含旧版本/tombstone，均不能由下面逻辑样本比例直接拆成业务物理字节。
[目录口径](mainnet-storage-distribution-2026-09-07.md)

## 本次热历史抽样

覆盖当前 live 热历史区块范围 **29,127,573–30,512,882**，固定 seed 20260907，
均匀分层抽取 128 个内部区块，再加首尾，共 **130 个完整区块、66,282 条有效状态变更**。
每个选中块读取全部 pack 和 repair 行，由生产 rawdb 读取逻辑还原有效记录。
130 块全部完成：没有空块、资源截断、未尝试块或解码错误。

以下分母是样本 **69,967,778 B 的逻辑 Prev 正文**，不是 SST 文件或全热库：

| 业务数据 | 变更记录数 | 旧值字节 | 样本旧值字节占比 |
| --- | ---: | ---: | ---: |
| `SystemDelegation/drax-0-aggregate` 委托关系总表 | 76 | 62,879,666 | **89.87%** |
| 账户主记录旧值 | 38,702 | 5,210,435 | **7.45%** |
| WitnessVoteState 投票状态 | 109 | 1,311,564 | **1.87%** |
| ContractStorage 合约存储槽旧值 | 11,608 | 314,496 | **0.45%** |
| AccountResourceAux 资源辅助状态 | 6,139 | 163,562 | **0.23%** |
| 其余，包括资产余额、单对委托资源记录、全局属性等 | 9,648 | 88,055 | **0.13%** |

这里的“账户主记录”包括余额、账户标志和时间等字段；权限、资产、资源等还分别有辅助 domain。
合约存储是 slot 的旧值，例如合约余额/授权映射可能落在其中；没有针对合约 ABI 与 slot 做语义解码，
不能进一步声称这部分中某一种代币余额占多少。

`SystemDelegation` 是存储 domain 名称，不表示系统交易；普通 freeze/unfreeze 等用户交易也会修改它。
`dr-` 记录一对委托关系的资源余额、到期等；本次其旧值只有 **16,660 B（0.024%）**。
占大头的是 `drax-0` **“某账户与哪些账户存在资源委托关系”的大地址列表**。
它与磁盘上的 `.kv` 随机访问索引不是同一个概念。

首轮 18 块样本的比例为 96.92%，扩展为 130 块后是 89.87%。这种变化说明数据重尾；
二者不能合并当作 148 个独立区块样本，也不能把任一结果当作全热库精确比例。

### 最大记录的实际解码

扩展样本的最大 `drax-0` 原值位于 block **30,356,695**、txNum **1,882,347,410**，
长度 **7,001,167 B = 6.677 MiB**。其 native 格式解析结果：

| 字段 | 实际内容/大小 |
| --- | ---: |
| FromAccounts | 0 个条目 |
| ToAccounts | **318,233 个地址条目**，每条 21 B |
| To 地址正文 | **6,682,893 B，95.454%** |
| 每条地址的长度前缀 | 318,233 B，4.545% |
| Account 地址及其余 framing | 41 B |
| unknown trailer | 0 B |

ToAccounts 表示该账户向外委托带宽/能量的对象目录；这里是条目数，没有另行核对地址去重。
这条记录的主要内容已经明确是地址正文，不能归咎于大段 JSON、protobuf 未知字段或格式标签。
仅省去每地址长度前缀，原值最多约少 4.55%；更大的机会在于**不同历史版本重复的大量列表内容**。

当前部署路径把整个关系列表编码成一个 KV value。列表增加/移除一个关系时，历史层保存该 key
的完整变更前原值；多次历史修改会留下多个几乎相同的大列表。相同字节的 no-op 不产生历史，
同一采集阶段的同 key 触碰会合并；不能说每次函数调用都产生一个 7 MB 历史版本。
持久历史保存 Prev，并没有再重复保存 Next。

## 冷历史不能沿用热样本的 89.87%

先用 8 个等距 tx 位置选择对应段，再加入物理体积最大的 5 个段和最后 canary 的前一段，
去重后共 **14 个历史段**。普通段每段按非空 tx-index 分层抽取 16 个 256-entry 连续窗口；
最后 32 块 canary 用 32 个窗口覆盖全部 5,266 个 tx-index entries。
共统计 **319,966 条记录**；所有窗口完整，没有预算截断，canary 的 21,747 条记录全部覆盖。

按固定 manifest 的文件长度记账，五个最大文件合计占 history `.seg` 的 **35.99%**；下表百分比仍仅对应

较早的几个时间段样本多由账户主记录占主导。例如 txNum 211,893,460–290,380,291 段：
账户 **81.22%**、合约存储 **10.74%**、资源辅助 **6.31%**。
最早段的样本则为账户 **44.83%**、投票状态 **39.51%**、witness 记录 **12.24%**。
靠近当前 cold 尾部的前一段，委托大列表在样本中占 **76.92%**；最后 32 块完整 canary 占 **95.87%**。

**本次跨时期冷历史样本中，主要逻辑旧值来源为账户旧值、委托关系总表旧版本，以及部分投票状态；
占比随时期/样本显著变化。**不能宣称全部 804.50 GiB 中有 90% 或 96% 是委托列表。
特别是“记录多”与“字节多”完全不同：130 块热样本中，仅 76 条委托总表变化占旧值正文近 90%。

第一轮冷抽样只有每段 8×16 个 tx entries，包含已知 canary 在内都未抽中 drax-0。
扩大后 canary 全记录结果精确重现此前完整解码的 48,242,830 B，证明第一轮是抽样漏掉稀疏大记录。
生产 V7 tx-index 包含普通交易和块末 final 变化；采样器没有按 domain、系统交易或 value 大小排除记录。
没有把第一轮零命中错误解释成“没有委托历史”。

## 积压为何持续存在

详细代码和日志证据见 [积压原因核对](gtron-history-backlog-causes-2026-09-07.md)。

1. **产生的历史量被大 value 放大。**小关系增删可产生 MB 级完整原值，进入热库后还要经历解包、
   冷文件构建、索引、验证、合并和热裁剪；仅提高通用压缩级别可能进一步拖慢首次转冷。
2. **深度同步优先导入，主动降低冷处理频率。**软水位 262,144 块；importer 忙时可继续推迟到
   524,288 块以上才强制小批次。busy 模式的块/txNum 批次目标是正常模式的四分之一，
   之后有 30–60 秒恢复窗口。这保证尝试前进，不构成积压或总磁盘空间的硬上限。
3. **主要缺口在冷覆盖之前。**当前热尾跨度 1,385,310 块，而在线保留窗口是 65,536 块。
   维护前已有冷覆盖但未删热副本只差 2,317 块，已经处理；它解释不了百万块的主体积压。
4. **没有把持久历史字节和剩余磁盘反馈到导入准入。**下载缓冲背压不等于历史库容量背压。
   事故前 89 分钟实际窗口，冷覆盖推进 68,510 块、eligible 边界推进 39,631 块，
   积压减少 28,879 块：按区块边界净消化约 **5.41 块/秒**，仍欠约 **132 万块**。
   当时已经在追赶，不能说冷化完全没运行或始终赶不上入口；也不能用此区块率代替物理回收率。
5. **满盘会反过来阻断转换。**事故直接失败点是 ancient 交易索引 ETL 的临时文件空间不足。
   转冷/merge/LSM 压实需要临时空间，而且已保存全部历史的语义要求先证明冷覆盖才能删热原像。

冷化可缩短热尾，但不是等量缩小总历史。此前新建 32 块冷文件并压实后总占用净减少只有 80 KiB；
必须同时处理业务数据布局和冷化调度，不能把“尽快搬成 seg”当作固定盘容量问题的完整解法。

## Erigon 3 的机制及可借鉴之处

依据固定 v3.6.0 commit `ecc2ad992b86b75f5aa26368918b3f428cc329e8`，
**近期 Prev 也先进入 chaindata 的 MDBX 表**，后续才转到 snapshots/history 等可查询文件。
稳定 latest 也会进入 domain 文件，不能把它的小 chaindata 与 gtron 当前全 latest 热布局直接比大小。
[正常热写入](https://github.com/erigontech/erigon/blob/ecc2ad992b86b75f5aa26368918b3f428cc329e8/db/state/history.go#L387)

| 环节 | Erigon 3 当前实现 | 对 gtron 的借鉴与边界 |
| --- | --- | --- |
| 组织 | 按 domain，按 key/txNum 组织历史，支持大/小值路径 | gtron 已有按 key 组织的字典/定位索引，V6 正文仍按 tx 顺序；可结合 key 聚簇与巨大 aggregate 拆分验证收益 |
| 首次冻结 | 默认 390,625 txNums 一个 step；首次关闭历史页级压缩，优先小 step 文件 | 把尽早完成可查询冷覆盖与后续加强压缩拆开；不是取消校验，也不是所有初始文件都不压缩 |
| 后续优化 | 对齐区间逐层 merge，使用完整压缩配置 | 新编码应比较整个 build/merge/read 成本与临时峰值，不能只比成品大小 |
| 热裁剪 | history、相应 inverted-index、调用者三个上界取最小值 | 保持完整冷值和索引共同覆盖证明，持续推进裁剪；用户要求保留全部历史仍可满足 |
| 调度 | 初始同步和链尖均触发维护；按积压给裁剪时间 | 持续维护并监测四项进度：生成、完整冷覆盖、热裁剪、物理回收；gtron 还需磁盘余量反馈 |
| 数据库维护 | MDBX 页复用，无 Pebble 式后台 SST compaction | 可减少一种维护竞争，但删除不保证立刻缩小文件，也不会消除大列表整值复制 |

源码：[首次冻结](https://github.com/erigontech/erigon/blob/ecc2ad992b86b75f5aa26368918b3f428cc329e8/db/state/history.go#L554)、
[优先构建](https://github.com/erigontech/erigon/blob/ecc2ad992b86b75f5aa26368918b3f428cc329e8/db/state/aggregator.go#L2340)、
[裁剪覆盖](https://github.com/erigontech/erigon/blob/ecc2ad992b86b75f5aa26368918b3f428cc329e8/db/state/history.go#L1028)、
[链尖维护](https://github.com/erigontech/erigon/blob/ecc2ad992b86b75f5aa26368918b3f428cc329e8/execution/execmodule/forkchoice.go#L903)。

没有相同 TRON 数据、相同机器的 Erigon/gtron 端到端 A/B，因此不能承诺几倍吞吐。
“直接持久 history journal 绕过 LSM”是我们另一个设计候选，不是上述 Erigon 已部署路径。
[完整主源核验和版本限制](erigon-history-storage-audit-2026-09-07.md)

建议优先级是：大列表按有序关系/页无损表达历史差异并设置完整锚点；其次拆分快速冻结与后续压缩；
同时加入按字节积压、临时峰值和剩余空间限制导入的控制。必须维持列表顺序、存在性、未知字段及
每个历史时点的查询结果。此前 delta 实验只在 32 块上证明历史正文减少 89.05%，编码耗时约 3.58 倍；
它支持“压缩潜力大、首次同步不宜直接使用最重编码”的判断，尚未成为生产格式或全链容量承诺。

## 证据与诊断边界

[本地数值转录](../../build/benchmarks/20260907-history-types/business-results-transcribed.json)
记录来源、字段口径、14 段分布、130 块热样本和最大 native value。14 段表格的全部转录数值及
130 块分类数值已分别序列化计算 SHA-256，与服务器原 JSON 计算结果一致。
manifest 记账总长度和此前目录 apparent-size 总量相差 4,500 B，分母单独保留，未混算。
服务器完整原始文件：

- 冷：`/var/tmp/gtron-format-lab-20260907/cold-types-v2-20260907T084950Z-4638/`
- 热：`/var/tmp/gtron-format-lab-20260907/hot-types-128-20260907T085203Z-5203/`
- 初步热样本：`/var/tmp/gtron-format-lab-20260907/hot-types-16-20260907T084623Z-3930/`

冷扫描读帧头/字典/索引并统计 Prev 长度，跳过 value 正文，不作全文件 SHA 或全链认证；
已有 canary 另有完整 reader/字节恢复验证。本次读取的冷段及配套文件 inode/size/mtime 和固定 manifest SHA 保持稳定。
热程序使用标准 Pebble ReadOnly 打开，全数据库文件目录前后 inode/size/mtime 相同，
只允许同 inode 的零字节 `LOCK` mtime 改变；未绕过数据库锁。
两者运行前后 maintenance hold 和四个 gtron/deploy unit inactive 检查均通过。

冷扩展抽样 38.751 秒，热扩展 2.205 秒；这是受限诊断的耗时，不是全历史扫描、压缩、迁移或同步吞吐。
所有源码/安装包先做独立测试与审查，使用纯 Go 独立二进制部署到 lab，未链接或替换 gtron 服务程序。
