# 多核冷化与持续追赶

用户要求把工作重心放在大幅消除冷化积压，利用服务器空闲 CPU，授权实现、GitHub 提交、服务器拉取构建部署与实测。保留全历史及当前数据库；物理格式的正确读取、完整校验、持久化发布后再裁剪仍是数据契约。

基线：9 月 8 日 11:06–14:57，同一进程导入 63.58 块/秒、冷化 56.07 块/秒，积压增加 103,855 块；最近五分钟 61.33 对 42.22。CPU 约 3.9 核，正文 65,536 块整段约 105 秒。此前小批和非阻塞调度已运行，但固定恢复与串行编码限制持续吞吐。

1. 正文 V2 保持 Source/Transform 的顺序和表依赖，按帧并行 Zstd，严格按原顺序落盘。worker 数、在途字节及超大帧均有边界，取消或错误必须等待 worker 退出并清理未发布输出。文件格式、校验、fsync、manifest 和热删除顺序不改变。
2. 事件 V4 的小帧压缩采用有界有序流水线，减少随后会丢弃的 protobuf 字段复制；unknown 字段、空值和重建记录必须完全一致。历史已存在并行压缩，针对重复逻辑 key 减少首遍 ETL 排序，不能删除任何历史版本。
3. throughput 使用新鲜 Pebble 和设备观测：没有硬压力、恢复/健康等级且设备 await 不超过 2ms 时，提高历史目标占空比到 80%/90%，将默认短恢复下限从 3 秒降到 250ms。未知、过期、引擎压力或较高 IO 延迟保持原有保守预算；更长的显式恢复配置保留。完整批次成本、失败退避、既有截止、共享互斥、字节及范围预算仍生效。短批加快后不能继续被固定等待吞掉收益。
4. 不凭理论倍数交付。固定同输入比较串行/并行构建和完整解码查询，覆盖取消、乱序完成、错误、超大输入及并发检测；本地及服务器原生测试通过后部署。同一 PID 内比较完整观测窗口的导入、冷化、裁剪及积压变化，同时记录 CPU/RSS、盘 IO、错误和历史查询。部署前后不同高度只作为实际运行观察，不称同输入 A/B。

并行压缩缩短 CPU 阶段，吞吐预算增加持续工作时间，二者分别计量。全历史最终容量不是本轮速度优化可以保证的结果。
