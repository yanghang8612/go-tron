# 独立待归档历史暂存层实施计划

对应[规格](../specs/2026-10-01-history-staging-store.md)。本计划是分阶段门禁，不授权立即启用或部署；首版保留 canonical 同库原子 writer 和现有冷文件格式。已有库首次启用新 reader 前，以独立离线脚本调用新 capable `gtron db history-staging` 子命令完成可迁桶的移交和统一路由初始化；普通启动不做旧库 lazy migration，也不双读 fallback。从创世运行仍在原库原子提交 canonical writer，近期未成熟尾桶仍由原库持有，后续按相同协议 handoff。每一阶段先通过原生 Sapling、定向 race、故障注入及真实独立 Pebble 恢复测试，再进入下一阶段。首版以**跨已移交桶的深 rewind 走 reset+replay**作为明确选择；在线旧高度 repair 拒绝，单独的停机 rehydrate 工具完成后才可执行此类修复。

## 0. 固定契约与盘点

1. 在 `core/rawdb/schema.go` 增加独立 staging 键前缀与版本化 source route/receipt/epoch，而不是散落手写键。写出二进制格式、桶 bounds、hash/domain separation、版本升级和未知版本拒启测试。永久 source retired marker 与 staging receipt 的含义不同，不复用现有 `StageSnapshotHotPrune`。配置要求 staging 路径不同于 chaindata/冷目录且同文件系统与不同文件系统都按独立 DB 处理。
2. 建立所有直接调用清单并以编译接口约束迁移：`core/rawdb/accessors_state_changeset*.go`、`state_changeset_shared*.go`、`core/state/snapshots/history_stream_build.go`、`cold_builder.go`、`domain_registry.go`、`core/state/history.go`、`core/tron_backend.go`、`core/state_history_index_stage.go`、`core/rawdb/accessors_derived_rebuild.go`、`core/state/pruning/worker.go`、`history_shared_chunk_gc.go`、`state_change_index_pruner.go`、`core/blockchain_rewind.go`、reset/fork paths，以及全部 offline inspect/export/repair/backup/bootstrap 工具。把只读诊断的 source-aware 与 fail-closed 能力明确区分。
3. 记录 source/target 的初始真实 allocated size、WAL/L0/compaction debt、cache、RSS/cgroup、设备物理读写及现有冷发布速率；没有此测量不设生产搬运速率或工期。首版候选总 cache 4 GiB 拆热 3.5/暂存 0.5 GiB，仅是压测起点，32 GiB cgroup 不变。
4. 固定外部离线任务契约：`inspect` 输出库存与损坏分类；`migrate` 只读冻结 eligible 桶/源身份/冷证明并产生 plan ID 和每桶最大行/空间预算；`apply --plan-id` 在有界 batch 中按运行时 receipt/claim/epoch 协议执行；`resume --job-id` 从 durable 阶段恢复；`inspect --verify-complete --plan-id` 验证 eligible 全部 adopted/source-cleared 或经认证 cold-only，以及 bucket 0/近期/partial 桶的确定源。JSON/JSONL 必须有版本、chain/source/target/candidate SHA、epoch、进度和非零错误码；plan 过期或不明身份拒绝。shell/Python 只编排命令与系统服务，不解析 Pebble。本阶段只设计这些接口，不添加看似可直接运行的占位脚本。
5. 增加持久 `MIGRATION_IN_PROGRESS` latch 和部署能力门禁：`gtron.service` 启动前、`start.sh`、root-owned release helper、旧版自动 rollback 与 space guard 的所有重启路径都检查 latch 和 staging-reader format/capability marker。候选 Linux binary 可预先构建验证，但不能被自动 timer 在旧布局上先发布、启动。旧 binary 自身不识别新 marker，须由这些外部入口拒启；离线全量验证后 latch 转为只允许固定 SHA capable binary 启动验收的 `VERIFIED_PENDING_ACTIVATION`，成功健康验收或原 inactive 服务的离线验收后才解除。锁存状态包含原 service/timer active/enabled 意图，脚本中断或断电后仍有效。

## 1. 双库启动与读者先行（writer 仍只写原库）

1. 为 staging 单独开 Pebble、锁及 close 生命周期，严格限制其 cache/memtable/compaction 并加入进程总内存预算。默认目录候选 `datadir/gtron/history-staging`，允许另一物理磁盘，但原库、暂存和冷目录路径必须互不包含；使用独立 metrics namespace，避免默认空 namespace 的注册冲突。启动顺序读取 reader capability marker，校验两库和冷目录的同一 chain identity/epoch。旧 reader 不认识 marker，必须由 systemd 启动前与 deployment/rollback helper 的外部 capability fence 拒绝旧版本，不能回退至不识别路由的 `889e96b7`。暂未移交时，新复合层等价于原读者。
2. 实现 `HistorySource`/`HistoryReadView`：在 `chainmu→routeMu` 下注册 route generation 与 cold manifest lease，固定 source buffer/durable MVCC、target MVCC、head/root；完整查询/冷构建/索引 ETL 期间保留各自 pin，释放顺序和取消/join 可测试。route 修改遵循 `indexMu→chainmu→routeMu`；任何 route 锁持有者不得等待 chain、I/O fsync、冷构建或压实。view 按桶决定唯一 hot owner，零行、正序 repair、重复/错 epoch、缺 chunk fail closed；跨桶范围仍按 block/tx/seq 顺序合并。跨库 snapshot 不是原子事务，正确性靠 target 先持久、route 后持久、cold 文件 lease 和 GC 读 pin。
3. 把 cold builder 的 cutoff/start tx-range、dictionary/record/tx-range 三遍，SnapshotBuild 崩溃恢复；archive/as-of RPC、按 key/prefix/batch lookup、generation change；posting 候选 authoritative 校验、index ETL 与 unwind 读取都迁到复合源。热 tx-range 保留使现有 cold 边界定位继续可用，但 route 必须决定 payload 来源。对没有 cold 证明且没有 source/stage 数据的高度报错；合法零 changeset 块仍正常。所有读者就绪前，**不启用源 payload 删除**。
4. 双库视图/race 测试覆盖 route 切换同时 RPC 与冷 build、source snapshot 先于 adoption、target snapshot 先于 release、冷 manifest 替换、旧 pin/GC、取消与 reader Close、tx-range 缺口、损坏/不存在 chunk、正序 repair 与不同 bucket 的有序 union。真实 Pebble 进程重开测试不可只用 memorydb 模拟。
5. 对现有库实现统一路由初始化屏障：staging-owned 桶有 durable receipt，已 cold-only 桶有完整冷证明，bucket 0、retention 与不完整近期尾桶明确 source-owned；没有 route 不触发旧库猜测。已冷裁剪的混合桶通过分区间证明，不补造 seq0 或已删除的 payload。cold-only 和 mixed-cold 都以 route 的版本化 cold-binding 登记持久 segment 依赖，immutable receipt 只记录原始认证事实；当前 manifest generation 不可当永久地址。所有查询、索引 ETL、冷 builder、unwind 共享同一 `HistorySource` 解释；普通启动只 reconcile route/receipt/manifest 与 binding 并验证屏障，新创世库由新版初始化其自身路由模型。

## 2. 仅复制试运行与 receipt

1. 新迁移 worker 独立于 cold Runner `passMu` 生命周期：在现有 canonical index→chain guard 的短闭包捕获 sealed source/route epoch proof，注册持久桶级 claim（ID、不可变写版本、epoch）与 pinned view；热裁剪、shared chunk GC、repair/rewind writer 必须尊重该 claim，不持 chain 锁等待长 copy。耗时 copy、源全键集摘要与目标校验在锁和 cold build/merge 序列外，adopt 前只重验 O(1) claim identity/版本、receipt 摘要与有界 guard 证明，不在 guard 内重扫 1024 桶。claim 的取消、崩溃恢复、过期撤销需证明源仍在且没有目标 route 后才能放行原热裁剪。准入完整 1024 桶，使用 verified canonical/solidified/Finish/StateHistoryIndex、retention、flush/settled 与 block hash/tx-range 连续性。已被冷清理的混合桶要求逐子区间完整冷覆盖证明；不能要求每块有 seq0。严格限定每次读字节、写 batch、并发桶数和取消检查；源视图与目标 receipt 的 exact key/value/物理摘要比对后继续逻辑解码认证。同设备总 I/O 公平额度协调 cold/transfer/compaction，不给两个 worker 各自一份可无限抢占的 heavy-work lease。copy 前预留当前桶目标副本、receipt/WAL 与两库压实临时空间，文件系统低水位不满足则暂停；就地搬运无需整库副本，但不能假设近满盘也能无空间工作。
2. 目标写行→`SyncKeyValue()`→目标 pinned 全量复核→receipt `TARGET_READY`→再次 `SyncKeyValue()`。复制失败、sync 失败、校验失败只产生 orphan，不发布源 route。先提供只读 dry run 与定量报告，包括 copied bytes、WAL/SST、源读、目标写、设备压实、延迟及错误。不要借用已有 256-block `ExportStateHistoryRange` 作为完整桶的移交证明。
3. 故障注入覆盖每 batch 中断、目标 WAL sync 错误、receipt sync 错误、重复迁移、manifest 在复制中换代、源 fork/canonical 变化、恰好桶边界及 max uint64 防溢、bucket 0 明确跳过而不伪造 genesis tx-range、旧桶缺 metadata/已 retired，以及碰撞、重复与不一致的共享 chunk。重开必须保留完整源、忽略或清理 orphan，绝不出现未经持久认证的新路由。
4. 离线 CLI 使用**同一** copy/receipt/claim 实现但单独的资格采集：它仅打开存储，不启动 node 生命周期。停止并排空 writer、独占原库/暂存库/冷目录和确认持久 flush，取代在线 `HistoryPrefixSettled` 的内存 overlay 证明；不能在 CLI 里伪造在线 settled。canonical/solid、durable Finish/Index、retention、冷 manifest 与每桶 tx-range/hash 仍逐一校验。`inspect` 的 cold-only/已 hot-pruned 合法空源、zero-copy 成功、最坏单行/单桶超限、低水位拒绝、过期 plan、CLI 重开与锁冲突都要有真实文件测试。

## 3. 源端采纳、分批删除和三边界统计

1. 确认部署 helper 的 reader-capability fence 已启用后，在 index→chain→route 顺序下重验 source claim/target receipt 和 guards，先禁止同桶旧高度新 writer，再在**原库一个 batch**原子写 `ADOPTED` route、retired marker、deletion intent；与读者 snapshot capture 同 routeMu 边界发表本进程 generation，立即放开 routeMu 后才调用原库 `SyncKeyValue()`。sync 失败不准删源，目标 receipt/任务 lease 保留待恢复或重新确认。route 可在 fsync 之前对同进程可见，但 target 已持久；重启按照原库是否恢复该 batch 分支处理。仍不承诺跨库 batch 原子。
2. route durable 后有界删除源 changeset/repair/chunks；原库 tx-range、全局 posting/directory、route/marker 仍保留。fresh source physical iterator 确认无残留后写 `SOURCE_CLEARED`。读者只用 receipt 指定的 owner，不尝试 source-first/target-fallback。任何删除中断可重试，不得将部分删除的源重新选为 authoritative。
3. 独立 `adopted`、`cold-certified`、`target-reclaimed` 每桶状态与派生连续水位，显示 epoch、last verified/hash、等待原因和 orphan 数。导出热库/暂存库 cache、WAL、L0、debt、stall、逻辑 tombstone、SST allocated bytes、物理 I/O/CPU/内存。`StageSnapshotHotPrune` 保持原意义。首次启用时一次只允许少量桶，人工审计 source/stage/冷等值与最坏调用时延，再决定增加速率。
4. 反复故障矩阵：adoption batch 前/后、原库 sync 前/后、每组 delete 中、retired marker 冲突、reader 已 pin 源、offline repair 并发、取消/kill -9/reopen。任何无法证明唯一数据副本的组合都 fail closed；源为空且 route 未 durable 的状态必须由测试证明无法产生。

## 4. 冷发布、目标退休、回滚与工具

1. 复合源喂给现有冷 trio 构建/完整自检与 manifest 原子发布；SnapshotBuild 仍由原库 hash-bound stage 记录、崩溃后按 manifest 与 stage reconcile。目标删除只在 cold-certified 全桶/缺口已核实、source route durable 释放、所有持久 cold-binding/source/target/manifest 依赖与同 epoch pin 退出后发生。新增文件内容身份→bindings 的有界反向索引；新增 publication 若不替代已引用文件则不重绑、不扫描全部历史。替代 merge 对受影响 mixed-cold、cold-only 路由，以经审计并覆盖内容/tx-range/行数的 merge transition 证据，缺失时用完整逻辑内容校验，证明新区间 canonical、tx-range、语义内容等价，再按索引有界批次原子更新版本化 binding/索引并 `SyncKeyValue()`。旧 trio/retired metadata 在 rebind 持久完成且旧 pin 退出前不得 GC；G+1 已发布但 rebind 未 sync 时重启须用仍保留的旧文件/当前 manifest 重新认证并幂等续跑，失败则保留旧依赖且停止相关回收。只匹配高度不授权换绑。依赖积压、额外核验 I/O 或高水位限制新的替代/移交，避免无界旧文件保留。目标删除/GC 与 source adoption 分别限速；fresh target iterator 及 manifest lease 复核后记录 `TARGET_CLEARED`，不把 tombstone 当成已释放空间。
2. 明确深 rewind：`canIncrementalUnwind` 改为对整个回滚区间检查实际 **source-owned 且未裁剪** changeset 覆盖；碰到 staging/cold 或无法认证的段即拒绝增量，但仍守现有 solid/共识边界。首版使用可重做的全量 reset+replay：破坏前核验 `[1,replayTarget]` 全部 block/body 可用及预定 canonical hash；将旧/新 epoch、目标 hash、重放终点、来源与冷可见性规则写入 `ResetMutablePrefixes` 不会清除的 durable `RESETTING` intent。该状态禁止普通启动、查询、移交、冷归档与维护；全部旧 `[1,replayTarget]` source/staging/cold owner 和 receipt 隔离，而非只处理 rewind 尾部。每次中断在保留 block 来源和 intent 下安全重做整个 mutable reset、genesis 与从块 1 的新 epoch `SOURCE` route/history/tx-range/stage 重放；未完成高度不得读取旧 owner，重放时不得并行 handoff/冷构建。完整 hash-bound Finish/Index、root/stage、route/历史覆盖与冷可见性核验且 sync 后，才 durable `RESET_COMPLETE` 放行，之后重新启用正常 handoff。测试 intent sync、epoch 切换、每段 mutable 删除、genesis、重放进度、冷隔离及完成屏障前后 kill/reopen，包含旧前缀多个 staging 和 cold-only 桶；每次须从同一 intent 续跑或安全重做，不能靠猜测缺口。缺 block 必须破坏前失败；运维 reset 不能绕开共识接受非法 fork。此首版不实现自动整桶 rehydrate 后再增量 unwind。
3. 旧高度 repair/restore 在线遇已移交桶即拒绝。独占停机 repair 工具按 receipt 和 canonical 校验整桶、复制所需 payload 回原库并 sync、在原库原子发布新 epoch `SOURCE` route，失效相应 cold tail，旧目标留到 pin 退出；只有重新建立完整热覆盖后才允许原 writer 进入。保留永久 retired 语义或经过独立验证安全地重建 shared bucket，不能删 marker 后继续引用旧 chunk。该工具与 reset+replay 路径分开实现和测试。
4. 停机 inspect/repair/export、全量备份/恢复、bootstrap、reset 都必须同时获得两库与冷目录的一致恢复点或拒绝执行；旧单库工具 fail closed。增加 staged target 损坏/丢失、source 已删/未删、冷文件已发布/未发布、部分目标 GC、旧二进制启动与错误 rollback、从双库备份恢复的真实进程测试。

## 5. 既有库首次启用的离线编排

1. 独立 shell/Python 脚本先核对经过原生 Sapling 构建/测试的新 Linux binary 的绝对路径、SHA、source revision、staging format/capability，且预先安装/验证 systemd、`start.sh`、release helper、rollback、space guard 对持久 latch 和 reader capability 的检查；记录 `gtron.service` 和 `gtron-deploy.timer` 的原 enabled/active 状态。构建候选和启用新 reader 分成两步：在旧布局上绝不先由 timer 发布并启动新节点。脚本先暂停 timer，停/等待当前 `gtron-deploy.service`，取得与 `/data/gtron/start.sh` 相同的 `/data/gtron/start.lock` 排他锁；确认无 deploy 作业后，原子 fsync 写持久 `MIGRATION_IN_PROGRESS` latch，再停 `gtron.service`，确认无旧进程并取得全部存储排他锁。**锁及 latch 前的失败还未进入迁移，不声称节点已停；**latch 后的失败保持停机和可续跑。只持 shell PID/`flock` 不构成断电后的保护。
2. 脚本用同一 capable binary 顺序运行 `inspect`、`migrate`、`apply` 或 `resume`、`inspect --verify-complete`。每次调用重新核对 latch/job、链及三个路径身份、source/candidate SHA 与冻结资格；不要求整库备份、不删除目录，不以现有 256-block 导出 API 搬 1024 桶。计划覆盖所有当时 eligible 完整桶，`--max-buckets=0` 可表示全部，但单行、单桶、单批、累计工作量、空间预留、deadline 和 I/O/内存都有硬界。已有 hot-pruned/cold-only 桶只记录已验证冷来源，bucket 0/部分/近期尾桶留下确定 source 路由，零复制也须完成全库存核验。成功出口要求每个 eligible 桶的 durable adoption、source-cleared、route 初始化屏障、唯一 query/index/cold source 和旧 reader guard 全通过。
3. 断电、kill、WAL/sync/磁盘满、空间低水位或任何证明失败，脚本返回具体 bucket、receipt 阶段、错误和续跑命令，保留节点停机、timer 暂停、latch 与双副本；不能用 `trap` 自动恢复旧服务或 rollback 旧 binary。`resume` 重开并 reconcile 后按相同协议重试，孤儿目标不能被读作历史。仅成功后安装并验证 capable release，将 latch 转为 `VERIFIED_PENDING_ACTIVATION`；原 active 服务只以固定 SHA capable binary 启动并通过 startup reconciliation/健康检查，原 inactive 服务以离线 verify 验收且不强行启动。然后持久写完成标记、解除 latch，按捕获的原 enabled/active 意图恢复 timer/service；原 disabled timer 不擅自启用。若原 timer active 而 service inactive，timer 尊重保留的 stop-intent 并继续 no-op。
4. 用真实 systemd/脚本集成测试自动部署与迁移的竞态：timer 刚触发、deploy.service 已在 build/test/rollback、迁移时重启主机、space guard 尝试 restart、原服务 inactive、原 timer disabled、旧 helper/旧 binary 启动、latch 未落盘/半写、成功解除 latch 前后崩溃。所有失败路径保持停机且可恢复，只有验收通过才恢复原运行意图。脚本先测试 hash/version mismatch 与多库锁冲突，确保 Python/shell 没有自行写 Pebble 或绕过 receipt。

## 6. 运行时闭环与故障验收

1. 在线扫描每页至多 256 桶，retirement 用独立可环绕 cursor；分别造纯热晚发布和 mixed partial→full-cold，证明迟到桶会被重新发现并回收。Target→Cold 用真实逻辑行、修复优先级和流式 Prev 摘要对照冷 trio；注入缺行与改 Prev，重复两轮均拒绝且旧 claim/ContentID 依赖不丢。
2. 查询、ETL、冷 builder 在任何 index/chain/route 锁之前取得可取消的 publication Read admission，只持到一致 route/热/暂存/冷 snapshot 与 file lease 捕获。merge 的 Write admission 只覆盖 G+1 Integrate、受影响 binding 有界批次认证/Sync 和新代切换；故障后同进程下一后台 pass 与重启都须 reconcile 后重新放行。记录 capture 等待时间，测试已有长读不阻昂贵 merge 构建且旧 file lease 仍保护读取。
3. 在线 reset 明确拒绝；离线完整 replay 后先持久隔离旧 active state-domain 冷 trio，使用新 epoch 私有路径重建并合并同一区间，证明旧 catalog/旧 pinned 文件 SHA 不变。旧 epoch target、cold refs、热 metadata 以三个独立持久有界 cursor 清理；当前 SOURCE receipts 留存，已清源桶回收。无旧 cold manifest 的 fresh reset、Sync 失败、分页中断和重启续跑都须覆盖。
4. 未知压力或空间证据 fail closed；监控 source/target/cold allocated bytes、独立 Pebble 压力、总设备物理 I/O、归档与搬运净吞吐。共享盘未新增带宽，隔离 LSM 本身不构成同步加速证据。

## 验收与上线决策

每阶段跑相关单元、race、重启 fault matrix、`make test-sapling`、`make gtron`、`go vet` 和历史 RPC/冷输出逐行字节 oracle。首次启用前必须有同步持续写入下的 reader/pin/GC 压测、单设备物理 I/O 与 32 GiB 峰值证据、部署 helper 防旧版回滚、离线 CLI/脚本断电续跑、两库备份恢复演练及安全停机路径。**首次正式启用顺序是先离线库存/移交/统一路由验收，后新节点启动**；候选可提前构建，不可提前由自动 timer 启用。现有积压按原位置逐桶搬运；不做整库备份或删库。判断收益使用同负载 cold publish 净进度、原库与暂存库总 allocated bytes、总写放大、设备延迟和热导入停顿，不能只看原库 `du` 降低或迁移桶数。本阶段尚无专门的线上迁移 I/O 容量实测，任何速率、耗时和 3.5/0.5 GiB cache 数值都待压测决定。
