# 冷化流水线与索引追赶

用户授权继续实现、测试、提交 GitHub 并在现有主网服务器部署。保留全部历史查询和现有数据库；不改变共识、公开 API 或已有冷文件读取格式。

## 基线与问题

9 月 9 日 09:38 前的连续观测：同步约 70–77 块/秒，状态冷化约 76–99 块/秒；正文 V2 约 98 块/秒，独立交易索引约 17 块/秒，后者债务已超过一千万块。索引同步中每五分钟只准入一个 8,192 块叶，理论上限 27.31 块/秒。机器 16 核，进程约使用 4 核，RSS 约 22.7 GiB，服务内存限额 40 GiB；共享盘 busy 约 73%，不能把空闲 CPU 等同于无限 I/O。

新 CPU profile 还显示串行 ETL radix、manifest 解析及目录扫描。已有压缩并行、manifest 解码缓存和 CDC 不重复作为本轮新增功能。

## 实施范围

1. 独立索引在新鲜、健康的存储观测下采用按实际整批耗时和债务计算的预算；未知或受压时保守回退。保留完整可恢复小批、共享重任务 gate、失败退避，加入有界独立唤醒，避免三十秒轮询和五分钟固定间隔限制吞吐。首次扫描得到的完整交易哈希在发布后复用删除；溢出有界存储，恢复可重扫。
2. 正文迁移维持串行读取和有序落盘，把独立记录的解码、校验、转换分批并行。调用者显式选择可并行纯处理；借用源数据先取得所有权，批次同时限制行数和字节，超大行单独处理。所有 worker 在错误/取消及返回前退出；训练、逐帧验证、持久化发布和热删除顺序不削弱。
3. 为 Manager 私有、已验证不可变 manifest 复用派生索引；外部可变对象采用调用内索引，复制时不携带可能过期的索引。优化 companion 平方扫描及每读重新扫描排序。紧凑 JSON 如采用，只改变序列化空白，保留校验、签名语义、原子替换与 fsync。
4. ETL 仅在大输入上并行互不重叠的 radix 分区，2–4 个 worker 复用现有内存；短分区、序列号、删除、合并及磁盘写入语义保持不变。

## 验证与上线

固定同输入对比单线程与并行完整构建、输出/查询及内存，覆盖取消、乱序完成、异常数据、借用缓冲和发布前不得删除。进行相关竞态检测、全仓检查和服务器原生构建测试；基准不得和其他重测试并发计时。部署后核对可执行文件身份，连续窗口分别计量同步、状态冷化、正文和索引覆盖/裁剪，连同 CPU/RSS、磁盘负载、错误和历史查询。不同高度观测只表示实际运行改善，不当作严格 A/B 或最终全历史容量保证。
