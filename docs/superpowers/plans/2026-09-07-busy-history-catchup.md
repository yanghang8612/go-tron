# 基于创世实测修正繁忙时历史冷化调度

用户已移除原数据库，并授权重新部署、从创世同步和通过 GitHub pull 交付。保留全部历史状态、固定磁盘与 MySQL 位置；不再次清空本轮新库。

## 实测问题

`f6ef2e03` 的 Linux Sapling 构建通过全仓测试并成功从创世运行。实际冷发布、热裁剪和固定账户历史查询均已闭环；但持续 importer busy 时，一批 1,250 块构建约 0.17 秒，之后仍等待 30 秒。两次完成间隔 30.181 秒、冷化 41.417 blocks/s、净追赶 −808.598 blocks/s。繁忙水位只保证启动工作，不能保证积压不增长。

## 局部修复

新增显式 `--history.catchup-mode=balanced|throughput`。默认 balanced 保持原行为；本服务器选择 throughput。

1. throughput 的 forced-busy 构建恢复现有正常 `BatchBlocks`/`BatchTxNums` 上限，生产为 5,000 / 390,625，仍完整收尾最后一个区块。测量到存储压力时不再额外缩成四分之一；硬性最低空闲空间准入仍优先拒绝新输出，已覆盖热历史仍可裁剪。
2. 成功 forced-busy 恢复采用 `max(3 秒, 4 × 实际维护墙钟, 共享 gate 配置冷却)`；昂贵工作不再受成功恢复 60 秒上限截断。乘法及截止时间必须处理溢出。
3. 失败或取消后至少等待原一分钟/正常配置间隔，或更长的成本恢复。独立截止时间必须先于 ready、accelerated、sync inactive 快路径检查；状态变化不能绕过已生效的恢复。
4. 计入 builder 返回后的完整 lifecycle 工作与后置错误。窄 completion 接口只最终化恢复及完成间隔，不重复计数发布/build 事件。standalone runner 自己完成计量；lifecycle 必须所有返回路径恰好完成一次。公共 API 的未完成交接不能允许另一个历史构建进入。
5. 不增加同时执行的 heavy job，不改文件格式、历史窗口、覆盖/校验、原子发布和冷发布后热裁剪次序。不以取消核验或放大冷输出并发制造吞吐。

这是以维护墙钟作为保守成本的调度策略，不是根据设备实际 IO 字节的精确预算，也不能保证任意后期业务都能追上导入。需要以实际同一进程内冷/热边界差分、同步速度、CPU/IO 和容量衡量。

- 本地定向、相关 race 和全仓验证；推送确定提交后服务器 pull，使用原生 CGO/Sapling 构建验证。
- 正常停止主网，保存第一轮采样和结束边界；保持全局维护锁及空间 guard，切新 release 后沿当前新库恢复。每次 PID 单独采样，重新校验原固定历史余额。
- 对比旧策略持续约 41 blocks/s 与新策略的实际完成速度；连续观察净追赶、cold/prune 同步推进以及导入性能。不能以一次快构建或早期小账户结果代替后期大委托输入的验收。
