# Hot L6 Bloom filters for unbounded exact reads

Based on 809815e72ede7f2bcbaf02c06ee7104800adec25. This changes neither logical keys/values, roots, MVCC, history retention, comparator identity, table format version, durability/sync order nor cache/worker/memtable budgets. Existing supported Bloom policy metadata is written into new hot L6 tables; no migration or forced compaction is run.

## Fixed read and writer policies

`Snapshot.NewGetCursor()` retains its zero-option behavior. The new `NewGetCursorWithOptions(GetCursorOptions{UseL6Filters:true})` fixes one private bool for the cursor lifetime. Its pooled getIter sets UseL6Filters only when opening L6. Default Snapshot.Get/DB.Get and default cursors reset the bool through their complete struct initialization. SST retention remains four entries. newIters requires the generated filter option to agree with that immutable bool and level; incompatible options retain uncached upstream construction, rather than incorrectly reusing a differently configured iterator. No early release of leased range spans or extra cache is introduced.

With the existing snapshot-Get backend selected (`GTRON_PEBBLE_BOUNDED_POINT_READ=get`), the adapter opts in for every unbounded cursor, including eager construction and failed-inner reconstruction at the same snapshot. Its current production caller is blockbuffer.PrefetchBatch; public interfaces also permit other unbounded callers. DirectHistoryStore forwards the unbounded request to both store snapshots and routes each key as before. Nonempty commitment-parent cursors stay on the default policy. Lookup timing, callback-scoped read-only ownership, deferred ReleaseValue across errors/panics, exact ErrNotFound handling, failed-inner discard/retry and Close error behavior are unchanged.

Upstream table_cache creates the raw range-deletion iterator independently before applying point filters. A Bloom-negative point lookup therefore still sees range tombstones and follows the original getIter merge, snapshot and visibility resolver. Custom comparer Split semantics remain the writer/reader's existing prefix policy. Filter read/checksum errors follow the existing error and cleanup path. Missing filter blocks use the original no-filter lookup, including old SSTs reopened with the new options.

`pebbledb.Options.EnableL6Filter` defaults false. Normal hot rawdb.DefaultPebbleOptions explicitly enables it, and NewPebbleDB uses those defaults; explicit NewPebbleDBWithOptions preserves its caller's choice. Main db_config takes those hot defaults. Direct-history and history-staging constructors explicitly retain false and do not gain new filter output. No CLI or adaptive threshold is added. The new writer option only sets the existing Bloom10 policy for level6 and retains existing compression/target sizing. This is independent from whether a reader elects to use a filter.

Existing L6 filter coverage is unknown: previous L6 compaction outputs generally omitted filters, but a trivial move can preserve an upper-level SST's filter. The new reader can use those existing filters immediately. Natural future compaction gradually increases coverage; no immediate effect across all~80GB hot L6 is promised. No live full-SST property survey or forced rewrite was performed.

## Evidence and accepted costs

The preceding four-slot/deepest-reservation/eight-slot experiments were rejected. Their large tiny-cache benefit came from one range-deletion block reread63→2times, and disappeared or regressed on actual BranchData without that artificial range-heavy shape. Read-ahead was not disabled to mask the result.

Ignored reader controls use identical sealed physical images per flag, actual production encoded BranchData and accessor-built storage keys with valid sibling missing slots. All563/1024missing requests lie within L6 table min/max, verified separately against ordinary Snapshot.Get and literal expected bytes. About55%missing matches the observed current prefetch mix, not bounded commitment's near100%hits. Four-entry request/open/reuse/fallback counts remain exactly equal between reader flags. True old no-filter SSTs reopen safely.

At16MiB cold cache, the mixed BranchData trace reduces VFS calls1714→919 and returned bytes5.326→3.746MB; storage1188→616 and4.842→2.685MB. New L6 SST size increases0.572% for BranchData and1.169% for the storage image. VFS ReadAt can hit the OS page cache and does not measure device traffic. These fixtures are~180MB/~14MB, not a mainnet size simulation.

Costs remain explicit: deep all-hit cold BranchData adds5.257→6.221MB; its16MiB process CPU sample10.885→11.722ms increases. Warm data with cold filter can add reads even in a55%missing workload. Second-pass warm data/filters can make both arms issue zero VFS reads, so CPU/allocation—not nonexistent IO savings—must be reported for that phase. A direct1MiB pressure probe grows reads5.487→45.376MB and CPU13.821→17.672ms. The normal adapter minimum is16MiB, but this stress result is retained without a new threshold or cache increase. Configured budgets, reservations, target and actual cache payload are recorded separately; entry counts do not bound retained block bytes or RSS.

This is conditional mechanism evidence, not controlled mainnet throughput or an isolated cause of cold-lag improvement. Local ARM64 short samples cannot establish AMD64 CPU improvement. Source tests, actual callback-prefetch/foreground/flush/reopen value oracles, separate ordered commitment root oracles, the included nested-module tests and focused races passed before freeze. The sealed-image integration is a functional oracle, not a performance comparison. Root go test ./... does not discover nested Pebble tests.
